# Recording Changes and Decisions

Part of Lion's developer guidelines, which start in [AGENTS.md](../AGENTS.md).

> **IMPORTANT**: `CHANGELOG.md`, `DECISIONS.md`, and the website's timeline `docs/changelog.html` are written from the model of Lion's development in `history/`. Never edit them by hand: record what changed as claims, run `bun run history write`, and commit the notes and the pages together.

The model holds one kind of record: a claim, a source's words and what they say. People write claims in `history/notes/`; readers recorded what each older commit said the same way. Rules in `history/core.json` derive which release shipped each claim from the commits that made it, so no claim says which release it is in, and each change or decision appears once, under the release that first shipped it, with every claim that says it as a source. The README section "Project Record" describes every file.

- **Record every change in the commit that makes it.** Add `history/notes/<topic>.json`, `{"claims": [...]}`, each claim `{"quote", "says"}`: the words a user of Lion reads, as the changelog shows them, with an example, and what they say in one of the five kinds the frame knows: a feature, a behavior, a rule, a decision, or a figure (see `history/research/README.md`). One text that says several things is several claims with the same words. A claim with no `"commits"` is made by the commit that adds its file, which is what you want for new work. Name the decision records a change follows in `"decisions"`. A `feat` or `fix` commit that no claim is made by fails `bun run history check` from then on, in the tests and in CI.
- **Record every design decision as something the model can check.** When a change chooses between ways Lion could behave, or sets a rule for how the project works, add a notes file with a `"title"`, the `"context"`, the `"decision"`, its `"consequences"`, and the `"alternatives"` with why each was not taken, and claims that quote that text: at least one decision claim, `{"decision": topic, "chose", "over", "because"}`, and one claim for each thing the decision asserts, the behavior, features, and rules it commits Lion to. The model checks each assertion against Lion at HEAD where a probe runs its case, so add a probe in `history/research/probes.json` for each behavior Lion can show, and for each one the repository can: a probe can list files with `repo/files`, read one with `repo/read` or `repo/json`, and run a command declared in `history/research/commands.json` with `repo/run`. A feature the decision asserts is there, or gone, takes a probe `{"feature", "kind", "program"}` whose program gives `true` or `false`. Reuse the topic of an earlier decision on the same question: deciding it again differently is a reversal, which the model derives. A breaking change follows a decision.
- **Let the pages count the commit they are in.** The pages count commits, and they are written before the commit that carries them exists, so that commit leaves itself out: the pre-commit hook passes, and `bun run history check` then fails by one. After you commit a change with its pages, run `bun run history write` again and commit what it changed on its own, as `docs: write the project record's pages for <commit>`. Then run it once more and `git commit --amend --no-edit` that pages commit: an amend replaces the commit instead of adding one, so the count now includes it. `bun run history check` says every page is up to date when it does.
- **Quote, do not paraphrase, when you cite a commit.** A commit can be named as `{"commit": "abc1234", "quote": "..."}`, and the check fails when the words are not in its message. Backfilled entries cite the commits that made them this way.
- **Releasing.** Add `history/releases/<date>-<name>.json` with what the release `"ships"` and a `"summary"`, run `bun run history write`, and commit. The release is at the commit that adds its file, and every change behind that commit not shipped before moves from "Unreleased" into its section. Tag the commit as `<name>@<version>` afterwards; `bun run history check` lists the releases that have no tag yet.
- **Ask the model.** `bun run history ask '<lion>'` evaluates any Lion expression against the model the last `write` or `check` built, such as `["why", ["shipped_in", "<claim>", "<release>"]]`.
- **Check a decision against the model before you make it.** The model reads every commit, the docs, the notes, and probes of Lion at HEAD, and rules that find where the project disagrees with itself: rules that contradict each other, behavior that breaks a rule in force, removals and breaking changes with no decision, figures that do not chain, docs that do not say what Lion does. `bun run history ask '<lion>'` asks it, such as `["query", ["predicted", "?rule", "lambda-extra-arguments", "?predicts", "?_"]]` for what the rules in force say a behavior should be. See `history/research/README.md`.
- **Keep the research current.** `bun run history check` fails on a finding that is neither in `history/research/known.json`, with a note, nor in `accepted.json`, with a reason, and on a listed finding that no longer holds. The record's tests run it. When a change brings a new finding, settle it with a decision or a fix, or list it in `known.json` and say so in your report; never accept one to make the check pass. Read the commits it lists as unread into a notes file as the README there says, and add a probe in `history/research/probes.json` for a behavior you change.
