    Lion documentation

    Everything Lion can do, organized by what you need right now: to learn, to get a job done, to look something up, or to understand why.

    Lion is a small Lisp whose programs are JSON. It evaluates on Effect, edits as a graph, runs from the command line, and includes a Datalog-style logic database.

    These docs follow the Diátaxis framework. There are four kinds of documentation, each written for a different need, and they are kept apart so each one can do its own job. Tutorials teach and how-to guides direct; both are practical. Reference and explanation inform; both are theoretical.

    Your first Lion program

    Build a small checkout calculator, one working step at a time, and learn how Lion reads JSON as code along the way.

    In this tutorial we will build a checkout calculator: given a cart total, it applies a discount for large orders and reports what the customer pays. Each step adds one idea and runs right here, so you can see every result as you go. You don't need to install anything.

    Step 1: Write a value

    Every Lion program is JSON. Start with the simplest program there is, a number. Edit it to any other number and watch the result follow.

    42
    result 
    42

    A record is a program too. Lion evaluates each of its values and keeps its keys:

    {"item": "lamp", "price": 120, "inStock": true}
    result 
    {"item":"lamp","price":120,"inStock":true}

    Numbers, booleans, null, and records of them come back as they are.

    Step 2: Call a function

    An array is a call. Its first element names the function, and the rest are its arguments. Add two prices:

    ["number/add", 120, 35]
    result 
    155

    The name number/add comes from Lion's standard library, which groups functions by module: number/, string/, array/, and so on.

    Step 3: Nest calls

    An argument can be another call. Lion evaluates the inner call first and passes its result on. Here is the cart total with 10% taken off:

    ["number/multiply",
  ["number/add", 120, 35],
  0.9]
    result 
    139.5

    Step 4: Name a value

    To use the total more than once, give it a name with define. To run several steps in order, wrap them in begin, which returns the last result:

    ["begin",
  ["define", "total", ["number/add", 120, 35]],
  ["number/multiply", "total", 0.9]]
    result 
    139.5

    Notice that the string "total" now stands for 155. A string that names something evaluates to what it names.

    Step 5: Write a function

    A lambda is a function you write yourself: a list of parameter names and a body. Define one that applies a discount rate to any amount:

    ["begin",
  ["define", "discounted",
    ["lambda", ["amount", "rate"],
      ["number/multiply", "amount", ["number/subtract", 1, "rate"]]]],
  ["discounted", 155, 0.1]]
    result 
    139.5

    Change 0.1 to 0.25 and the result changes with it.

    Step 6: Make a decision

    Only large orders get the discount. cond checks conditions in order and returns the result next to the first one that holds:

    ["begin",
  ["define", "total", 155],
  ["cond",
    [["number/greaterThan", "total", 100], "discount"],
    ["else", "full price"]]]
    result 
    "discount"

    Try a total of 80.

    Step 7: Put it together

    Now combine everything into the calculator. A function that takes a list of prices adds them up, works out the discount, and returns a record, so the result shows each part of the checkout:

    ["begin",
  ["define", "rate",
    ["lambda", ["total"],
      ["cond",
        [["number/greaterThan", "total", 100], 0.1],
        ["else", 0]]]],
  ["define", "receipt",
    ["lambda", ["total"],
      {"total": "total",
       "discount": ["number/multiply", "total", ["rate", "total"]],
       "pay": ["number/multiply", "total", ["number/subtract", 1, ["rate", "total"]]]}]],
  ["define", "checkout",
    ["lambda", ["prices"],
      ["receipt", ["aggregate/sum", "prices"]]]],
  ["checkout", ["array/make", 120, 35]]]
    result 
    {"total":155,"discount":15.5,"pay":139.5}

    Change the prices in ["array/make", 120, 35] to 40, 35 and the discount disappears.

    What we built

    We wrote a working program in plain JSON. Along the way we used values, calls, names, functions, decisions, and records, which is most of the core language. Because the program is JSON, you could store it in a database, send it over HTTP, or have another program write it.

    Next, the tutorial Build a family tree uses the same JSON to ask questions of a logic database. To look up the forms used here, see Special forms; to learn how names work, read Names, scope, and environments.

    Build a family tree

    Store facts about a family, then ask Lion's logic database to work out grandparents, ancestors, and more, all in JSON.

    In this tutorial we will record a small family and let Lion's logic database answer questions about it: who is whose grandparent, who descends from whom, and who has no children yet. At the end we will protect the tree from impossible data.

    Each step shows the whole program so far, because every example runs on its own. New lines are at the end.

    Step 1: Declare a relation and add facts

    A relation is a table with named columns. Declare parent, then add four facts to it. The fact form returns the facts it added:

    ["begin",
  ["relation", "parent", ["parent", "child"]],
  ["fact",
    ["parent", "ada", "bea"],
    ["parent", "ada", "cal"],
    ["parent", "bea", "dot"],
    ["parent", "dot", "eli"]]]
    result 
    [
  ["parent","ada","bea"],
  ["parent","ada","cal"],
  ["parent","bea","dot"],
  ["parent","dot","eli"]
]

    Step 2: Ask a question

    A query asks for every way to fill in the strings that start with ?. Those are logic variables. Ask who Ada's children are:

    ["begin",
  ["relation", "parent", ["parent", "child"]],
  ["fact",
    ["parent", "ada", "bea"],
    ["parent", "ada", "cal"],
    ["parent", "bea", "dot"],
    ["parent", "dot", "eli"]],
  ["query", ["parent", "ada", "?child"]]]
    result 
    [{"child":"bea"},{"child":"cal"}]

    There is one answer per child, keyed by the variable's name. Try ["parent", "?who", "dot"] to ask who Dot's parent is.

    Step 3: Write a rule

    A rule derives new facts. A grandparent is a parent of a parent, so the rule says: ?g is a grandparent of ?c when ?g is a parent of some ?p and ?p is a parent of ?c.

    ["begin",
  ["relation", "parent", ["parent", "child"]],
  ["relation", "grandparent", ["grandparent", "child"]],
  ["fact",
    ["parent", "ada", "bea"],
    ["parent", "ada", "cal"],
    ["parent", "bea", "dot"],
    ["parent", "dot", "eli"]],
  ["rule", ["grandparent", "?g", "?c"],
    ["parent", "?g", "?p"],
    ["parent", "?p", "?c"]],
  ["query", ["grandparent", "?g", "?c"]]]
    result 
    [{"g":"ada","c":"dot"},{"g":"bea","c":"eli"}]

    Step 4: Follow the line all the way back

    An ancestor is a parent, or an ancestor of a parent. A relation can refer to itself, so two rules cover both cases:

    ["begin",
  ["relation", "parent", ["parent", "child"]],
  ["relation", "ancestor", ["ancestor", "person"]],
  ["fact",
    ["parent", "ada", "bea"],
    ["parent", "ada", "cal"],
    ["parent", "bea", "dot"],
    ["parent", "dot", "eli"]],
  ["rule", ["ancestor", "?a", "?p"], ["parent", "?a", "?p"]],
  ["rule", ["ancestor", "?a", "?p"],
    ["ancestor", "?a", "?mid"],
    ["parent", "?mid", "?p"]],
  ["query", ["ancestor", "?who", "eli"], {"order": "who"}]]
    result 
    [{"who":"ada"},{"who":"bea"},{"who":"dot"}]

    Eli's ancestors come back sorted, because the query asked for {"order": "who"}.

    Step 5: Ask what is missing

    Who has no children? Declare who is in the family, then use not to keep only the people with no parent fact of their own. ?_ means "anything, I don't care what":

    ["begin",
  ["relation", "person", ["name"]],
  ["relation", "parent", ["parent", "child"]],
  ["relation", "childless", ["name"]],
  ["fact", ["person", "ada"], ["person", "bea"], ["person", "cal"],
    ["person", "dot"], ["person", "eli"]],
  ["fact",
    ["parent", "ada", "bea"],
    ["parent", "ada", "cal"],
    ["parent", "bea", "dot"],
    ["parent", "dot", "eli"]],
  ["rule", ["childless", "?p"],
    ["person", "?p"],
    ["not", ["parent", "?p", "?_"]]],
  ["query", ["childless", "?name"]]]
    result 
    [{"name":"cal"},{"name":"eli"}]

    Step 6: Count descendants

    A rule can count. Put aggregate/count in the rule's head, and Lion counts the matches for each ancestor:

    ["begin",
  ["relation", "parent", ["parent", "child"]],
  ["relation", "ancestor", ["ancestor", "person"]],
  ["relation", "descendants", ["ancestor", "count"]],
  ["fact",
    ["parent", "ada", "bea"],
    ["parent", "ada", "cal"],
    ["parent", "bea", "dot"],
    ["parent", "dot", "eli"]],
  ["rule", ["ancestor", "?a", "?p"], ["parent", "?a", "?p"]],
  ["rule", ["ancestor", "?a", "?p"],
    ["ancestor", "?a", "?mid"],
    ["parent", "?mid", "?p"]],
  ["rule", ["descendants", "?a", ["aggregate/count", "?p"]],
    ["ancestor", "?a", "?p"]],
  ["query", ["descendants", "?ancestor", "?count"], {"order": "-count"}]]
    result 
    [
  {"ancestor":"ada","count":4},
  {"ancestor":"bea","count":2},
  {"ancestor":"dot","count":1}
]

    Step 7: Collect answers into a list

    A query gives one record per answer. To put answers inside a value of our own, we use find: it takes a template and a goal, and returns the template's value for every match, as a sorted list. Here the template is a pair, a person and the list of their children, and that list is a find too:

    ["begin",
  ["relation", "person", ["name"]],
  ["relation", "parent", ["parent", "child"]],
  ["fact", ["person", "ada"], ["person", "bea"], ["person", "cal"],
    ["person", "dot"], ["person", "eli"]],
  ["fact",
    ["parent", "ada", "bea"],
    ["parent", "ada", "cal"],
    ["parent", "bea", "dot"],
    ["parent", "dot", "eli"]],
  ["find",
    ["array/make", "?p", ["find", "?child", ["parent", "?p", "?child"]]],
    ["person", "?p"]]]
    result 
    [
  ["ada",["bea","cal"]],
  ["bea",["dot"]],
  ["cal",[]],
  ["dot",["eli"]],
  ["eli",[]]
]

    The inner find is asked once for each person. Cal and Eli have no children, so they get an empty list instead of being left out, which the count in step 6 could not do.

    Step 8: Ask why

    why explains a fact: which rule produced it, and from which facts. Ask why Ada is an ancestor of Eli:

    ["begin",
  ["relation", "parent", ["parent", "child"]],
  ["relation", "ancestor", ["ancestor", "person"]],
  ["fact",
    ["parent", "ada", "bea"],
    ["parent", "bea", "dot"],
    ["parent", "dot", "eli"]],
  ["rule", ["ancestor", "?a", "?p"], ["parent", "?a", "?p"]],
  ["rule", ["ancestor", "?a", "?p"],
    ["ancestor", "?a", "?mid"],
    ["parent", "?mid", "?p"]],
  ["why", ["ancestor", "ada", "eli"]]]
    result 
    {
  "fact": ["ancestor","ada","eli"],
  "rule": [
    "rule",
    ["ancestor","?a","?p"],
    ["ancestor","?a","?mid"],
    ["parent","?mid","?p"]
  ],
  "because": [
    {
      "fact": ["ancestor","ada","dot"],
      "rule": [
        "rule",
        ["ancestor","?a","?p"],
        ["ancestor","?a","?mid"],
        ["parent","?mid","?p"]
      ],
      "because": [
        {
          "fact": ["ancestor","ada","bea"],
          "rule": ["rule",["ancestor","?a","?p"],["parent","?a","?p"]],
          "because": [{"fact":["parent","ada","bea"],"given":true}]
        },
        {"fact":["parent","bea","dot"],"given":true}
      ]
    },
    {"fact":["parent","dot","eli"],"given":true}
  ]
}

    Read it from the outside in: Ada is an ancestor of Eli because she is an ancestor of Dot, who is Eli's parent, and so on down to facts that were given.

    Step 9: Protect the tree

    Nobody can be their own ancestor. An invariant tells the database a question that must never have an answer. Add it, then try a fact that would make Eli Ada's parent:

    ["begin",
  ["relation", "parent", ["parent", "child"]],
  ["relation", "ancestor", ["ancestor", "person"]],
  ["fact",
    ["parent", "ada", "bea"],
    ["parent", "bea", "dot"],
    ["parent", "dot", "eli"]],
  ["rule", ["ancestor", "?a", "?p"], ["parent", "?a", "?p"]],
  ["rule", ["ancestor", "?a", "?p"],
    ["ancestor", "?a", "?mid"],
    ["parent", "?mid", "?p"]],
  ["invariant", ["ancestor", "?x", "?x"], {"assert": "none"}],
  ["fact", ["parent", "eli", "ada"]]]
    error 
    LogicError: Adding this fact breaks an invariant, so nothing changed. The invariant expected no answers but found 4, such as {"x":"ada"}: ["ancestor","?x","?x"].

    The database refuses the fact and tells us why: with it, Ada would be her own ancestor. The tree stays as it was. Change the last fact to ["parent", "eli", "fay"] and the program succeeds.

    What we built

    We stored facts, derived new ones with rules, followed a relationship through any number of generations, asked about what was missing, counted, collected answers into lists, explained an answer, and guarded the data with an invariant. Every part was plain JSON.

    Run an order desk

    Track orders whose status changes over time, keep the data consistent with an invariant, and save the whole desk as a Lion program.

    In this tutorial we will run a small order desk. Orders change status as they move along, the desk refuses changes that would leave the data inconsistent, and at the end we save everything to a file. We will build on the logic forms from Build a family tree.

    Step 1: Keep one row per order

    Each order has an id, a customer, a status, and an amount. Give the relation a key, {"key": "id"}, so it holds at most one row per id:

    ["begin",
  ["relation", "order", ["id", "customer", "status", "amount"], {"key": "id"}],
  ["fact",
    ["order", 1, "ana", "open", 30],
    ["order", 2, "ana", "open", 20],
    ["order", 3, "bo", "open", 50]],
  ["query", ["order", "?id", "?customer", "?status", "?amount"], {"order": "id"}]]
    result 
    [
  {"id":1,"customer":"ana","status":"open","amount":30},
  {"id":2,"customer":"ana","status":"open","amount":20},
  {"id":3,"customer":"bo","status":"open","amount":50}
]

    Step 2: Change an order's status

    To move order 1 along, add a fact with the same id. Because id is the key, the new row replaces the old one instead of sitting next to it:

    ["begin",
  ["relation", "order", ["id", "customer", "status", "amount"], {"key": "id"}],
  ["fact",
    ["order", 1, "ana", "open", 30],
    ["order", 2, "ana", "open", 20],
    ["order", 3, "bo", "open", 50]],
  ["fact", ["order", 1, "ana", "paid", 30]],
  ["query", ["order", "?id", "?customer", "?status", "?amount"], {"order": "id"}]]
    result 
    [
  {"id":1,"customer":"ana","status":"paid","amount":30},
  {"id":2,"customer":"ana","status":"open","amount":20},
  {"id":3,"customer":"bo","status":"open","amount":50}
]

    Step 3: Total what each customer owes

    A rule with aggregate/sum in its head adds up the amounts of each customer's open orders:

    ["begin",
  ["relation", "order", ["id", "customer", "status", "amount"], {"key": "id"}],
  ["relation", "owed", ["customer", "total"]],
  ["fact",
    ["order", 1, "ana", "paid", 30],
    ["order", 2, "ana", "open", 20],
    ["order", 3, "bo", "open", 50]],
  ["rule", ["owed", "?c", ["aggregate/sum", "?amount"]],
    ["order", "?_", "?c", "open", "?amount"]],
  ["query", ["owed", "?customer", "?total"], {"order": "customer"}]]
    result 
    [{"customer":"ana","total":20},{"customer":"bo","total":50}]

    Change order 3 to "paid", and Bo drops out of the answer.

    Step 4: Refuse to ship without an address

    An order must not ship to a customer without an address. Store addresses, and add an invariant: a question that must never have an answer. Then try to ship Bo's order:

    ["begin",
  ["relation", "order", ["id", "customer", "status", "amount"], {"key": "id"}],
  ["relation", "address", ["customer", "street"], {"key": "customer"}],
  ["fact",
    ["order", 1, "ana", "paid", 30],
    ["order", 3, "bo", "open", 50]],
  ["fact", ["address", "ana", "1 Elm St"]],
  ["invariant",
    ["and", ["order", "?id", "?c", "shipped", "?_"], ["not", ["address", "?c", "?_"]]],
    {"assert": "none"}],
  ["fact", ["order", 3, "bo", "shipped", 50]]]
    error 
    LogicError: Adding this fact breaks an invariant, so nothing changed. The invariant expected no answers but found 1, such as {"id":3,"c":"bo"}: ["and",["order","?id","?c","shipped","?_"],["not",["address","?c","?_"]]].

    The desk refuses: the change would ship order 3 to a customer with no address. Nothing changed, so order 3 is still open.

    Step 5: Make both changes at once

    Bo sends an address. A single fact form can add the address and ship the order together. The invariant is checked once the whole form is done, so this succeeds:

    ["begin",
  ["relation", "order", ["id", "customer", "status", "amount"], {"key": "id"}],
  ["relation", "address", ["customer", "street"], {"key": "customer"}],
  ["fact",
    ["order", 1, "ana", "paid", 30],
    ["order", 3, "bo", "open", 50]],
  ["fact", ["address", "ana", "1 Elm St"]],
  ["invariant",
    ["and", ["order", "?id", "?c", "shipped", "?_"], ["not", ["address", "?c", "?_"]]],
    {"assert": "none"}],
  ["fact", ["address", "bo", "9 Oak Ave"], ["order", 3, "bo", "shipped", 50]],
  ["query", ["order", "?id", "?customer", "?status", "?_"], {"order": "id"}]]
    result 
    [
  {"id":1,"customer":"ana","status":"paid"},
  {"id":3,"customer":"bo","status":"shipped"}
]

    Step 6: Save the desk

    ["snapshot"] writes the whole database as a Lion program: its relations, facts, and invariant. Running that program rebuilds the desk exactly.

    ["begin",
  ["relation", "order", ["id", "customer", "status", "amount"], {"key": "id"}],
  ["relation", "address", ["customer", "street"], {"key": "customer"}],
  ["fact", ["order", 1, "ana", "paid", 30], ["order", 3, "bo", "shipped", 50]],
  ["fact", ["address", "ana", "1 Elm St"], ["address", "bo", "9 Oak Ave"]],
  ["invariant",
    ["and", ["order", "?id", "?c", "shipped", "?_"], ["not", ["address", "?c", "?_"]]],
    {"assert": "none"}],
  ["snapshot"]]
    result 
    [
  "begin",
  [
    "relation",
    "order",
    ["id","customer","status","amount"],
    {"key":["id"]}
  ],
  [
    "relation",
    "address",
    ["customer","street"],
    {"key":["customer"]}
  ],
  [
    "fact",
    ["order",1,"ana","paid",30],
    ["order",3,"bo","shipped",50]
  ],
  [
    "fact",
    ["address","ana","1 Elm St"],
    ["address","bo","9 Oak Ave"]
  ],
  [
    "invariant",
    [
      "and",
      ["order","?id","?c","shipped","?_"],
      ["not",["address","?c","?_"]]
    ],
    {"assert":"none"}
  ]
]

    On your own machine, the lion command does this for you. Save the program from Step 5 as desk.json and run it with a database file; later programs then run against the saved desk, and the invariant still guards it:

    bun add --dev @lionlang/cli
bun run lion desk.json --database store.json

    What we built

    We kept one row per order with a key, changed statuses by adding facts, totaled what customers owe, refused an inconsistent change with an invariant, made two changes together, and saved the desk as a Lion program.

    To use these features in your own project, see Enforce rules on your data and Save and load a logic database. To understand why a change is all or nothing, read One set of rules for every feature.

    Sort an inbox

    Describe the orders you expect with a schema, find what is wrong with the ones that do not fit, and let rules take the good ones apart.

    In this tutorial we will sort an inbox of orders that arrive as JSON. Some are well formed and some are not. We will say what an order must be, see exactly where a bad one goes wrong, and write rules that keep the good ones and take them apart. We will build on the logic forms from Build a family tree.

    Step 1: Say what an order is

    A schema says what a value must be, and anything can be one. Write the record we expect, with a schema in place of each value: a function such as value/integer? for a value it accepts, and schema/anyOf for a choice. schema/fits? asks whether a value fits:

    ["begin",
  ["define", "Order",
    {"id": "value/integer?",
     "status": ["schema/anyOf", "open", "shipped"],
     "lines": ["schema/arrayOf",
       {"sku": "value/string?", "qty": "value/integer?"}]}],
  ["define", "mail",
    ["quote", {"id": 1, "status": "open", "lines": [{"sku": "tea", "qty": 2}]}]],
  ["schema/fits?", "mail", "Order"]]
    result 
    true

    The order fits: it has the three keys, and each value fits the schema under its key.

    Step 2: Find what is wrong

    The next order in the mail is a mess. schema/problems lists every place where a value does not fit:

    ["begin",
  ["define", "Order",
    {"id": "value/integer?",
     "status": ["schema/anyOf", "open", "shipped"],
     "lines": ["schema/arrayOf",
       {"sku": "value/string?", "qty": "value/integer?"}]}],
  ["define", "mail",
    ["quote", {"id": "2", "status": "opne", "lines": [{"sku": "tea"}], "gift": true}]],
  ["schema/problems", "mail", "Order"]]
    result 
    [
  {"path":["gift"],"found":true},
  {"path":["id"],"expected":"value/integer?","found":"2"},
  {"path":["lines",0,"qty"],"expected":"value/integer?"},
  {
    "path": ["status"],
    "expected": ["schema/anyOf","open","shipped"],
    "found": "opne"
  }
]

    There are four. Each has the path to the part that is wrong. The id and the status have the wrong value, so they show what was expected and what was found. The first line has no qty, so it shows only what was expected. And gift is a key the schema does not name, so it shows only what was found: a record fits a record with the same keys.

    Step 3: Give the schemas names

    schema declares a schema under a name, the way relation declares a relation. The name is then a predicate, and other schemas can use it. Let us also ask for more: a quantity must be above zero, which a lambda can say, and an order may have a note, which schema/optional allows:

    ["begin",
  ["schema", "Line",
    {"sku": "value/string?",
     "qty": ["schema/allOf", "value/integer?",
       ["lambda", ["n"], ["number/greaterThan", "n", 0]]]}],
  ["schema", "Order",
    {"id": "value/integer?",
     "status": ["schema/anyOf", "open", "shipped"],
     "lines": ["schema/arrayOf", "Line"],
     "note": ["schema/optional", "value/string?"]}],
  {"with a note": ["Order",
     ["quote", {"id": 1, "status": "open", "lines": [], "note": "gift"}]],
   "no tea": ["Order",
     ["quote", {"id": 1, "status": "open", "lines": [{"sku": "tea", "qty": 0}]}]]}]
    result 
    {"with a note":true,"no tea":false}

    Change the 0 to a 3, and the second order fits too.

    Step 4: Keep the orders that fit

    Now put the mail in a relation, one document per row. A relation call takes a schema for each column, so ["inbox", "Order"] would ask for the rows that are orders. We want more than that: the id and the status of each. A logic variable in a schema takes the value it meets, so a record with variables in it is a pattern. schema/allOf asks for both at once, and schema/open lets the pattern name only the keys it wants:

    ["begin",
  ["schema", "Line",
    {"sku": "value/string?",
     "qty": ["schema/allOf", "value/integer?",
       ["lambda", ["n"], ["number/greaterThan", "n", 0]]]}],
  ["schema", "Order",
    {"id": "value/integer?",
     "status": ["schema/anyOf", "open", "shipped"],
     "lines": ["schema/arrayOf", "Line"]}],
  ["relation", "inbox", ["doc"]],
  ["relation", "order", ["id", "status"], {"key": "id"}],
  ["fact",
    ["inbox", ["quote", {"id": 1, "status": "open",
      "lines": [{"sku": "tea", "qty": 2}, {"sku": "cup", "qty": 1}]}]],
    ["inbox", ["quote", {"id": 2, "status": "opne", "lines": []}]],
    ["inbox", ["quote", {"id": 3, "status": "shipped",
      "lines": [{"sku": "tea", "qty": 5}]}]]],
  ["rule", ["order", "?id", "?status"],
    ["inbox", ["schema/allOf", "Order",
      ["schema/open", {"id": "?id", "status": "?status"}]]]],
  ["query", ["order", "?id", "?status"], {"order": "id"}]]
    result 
    [{"id":1,"status":"open"},{"id":3,"status":"shipped"}]

    Orders 1 and 3 are kept. Order 2 says "opne", so it is not an order, and the rule passes over it.

    Step 5: Say why the rest was rejected

    A document that was passed over should not vanish. schema/problems gives a list, and in turns a list into rows, so a second rule records each problem of each document:

    ["begin",
  ["schema", "Line",
    {"sku": "value/string?",
     "qty": ["schema/allOf", "value/integer?",
       ["lambda", ["n"], ["number/greaterThan", "n", 0]]]}],
  ["schema", "Order",
    {"id": "value/integer?",
     "status": ["schema/anyOf", "open", "shipped"],
     "lines": ["schema/arrayOf", "Line"]}],
  ["relation", "inbox", ["doc"]],
  ["relation", "rejected", ["id", "where"]],
  ["fact",
    ["inbox", ["quote", {"id": 1, "status": "open",
      "lines": [{"sku": "tea", "qty": 2}, {"sku": "cup", "qty": 1}]}]],
    ["inbox", ["quote", {"id": 2, "status": "opne", "lines": []}]],
    ["inbox", ["quote", {"id": 4, "status": "open",
      "lines": [{"sku": "tea", "qty": 0}]}]]],
  ["rule", ["rejected", "?id", ["object/get", "?problem", "path"]],
    ["inbox", "?doc"],
    ["schema/fits?", "?doc", ["schema/open", {"id": "?id"}]],
    ["in", "?problem", ["schema/problems", "?doc", "Order"]]],
  ["query", ["rejected", "?id", "?where"], {"order": "id"}]]
    result 
    [{"id":2,"where":["status"]},{"id":4,"where":["lines",0,"qty"]}]

    Order 1 has no problems, so it has no rows. Here schema/fits? is a goal of its own: it checks a value that another goal bound, and binds ?id from it.

    Step 6: Take the lines apart

    Each order holds a list of lines. The element of in can be a pattern too, so one goal takes the list out of the order and the next takes each line apart. With the lines as rows, an aggregate can total the units of each product:

    ["begin",
  ["schema", "Line",
    {"sku": "value/string?",
     "qty": ["schema/allOf", "value/integer?",
       ["lambda", ["n"], ["number/greaterThan", "n", 0]]]}],
  ["schema", "Order",
    {"id": "value/integer?",
     "status": ["schema/anyOf", "open", "shipped"],
     "lines": ["schema/arrayOf", "Line"]}],
  ["relation", "inbox", ["doc"]],
  ["relation", "line", ["order", "sku", "qty"]],
  ["relation", "units", ["sku", "total"]],
  ["fact",
    ["inbox", ["quote", {"id": 1, "status": "open",
      "lines": [{"sku": "tea", "qty": 2}, {"sku": "cup", "qty": 1}]}]],
    ["inbox", ["quote", {"id": 2, "status": "opne", "lines": []}]],
    ["inbox", ["quote", {"id": 3, "status": "shipped",
      "lines": [{"sku": "tea", "qty": 5}]}]]],
  ["rule", ["line", "?order", "?sku", "?qty"],
    ["inbox", ["schema/allOf", "Order",
      ["schema/open", {"id": "?order", "lines": "?lines"}]]],
    ["in", {"sku": "?sku", "qty": "?qty"}, "?lines"]],
  ["rule", ["units", "?sku", ["aggregate/sum", "?qty"]],
    ["line", "?order", "?sku", "?qty"]],
  {"lines": ["find", ["array/make", "?order", "?sku", "?qty"],
     ["line", "?order", "?sku", "?qty"]],
   "units": ["query", ["units", "?sku", "?total"], {"order": "sku"}]}]
    result 
    {
  "lines": [[1,"cup",1],[1,"tea",2],[3,"tea",5]],
  "units": [{"sku":"cup","total":1},{"sku":"tea","total":7}]
}

    Step 7: Guard the shelf

    The sorted orders live in a relation of their own. To make sure nothing else ever puts a bad row there, give the relation a schema. Every row, taken as a record of its columns, must then fit it, and a change that would add a row that does not is refused:

    ["begin",
  ["schema", "Shelved",
    {"id": "value/integer?", "status": ["schema/anyOf", "open", "shipped"]}],
  ["relation", "order", ["id", "status"], {"key": "id", "schema": "Shelved"}],
  ["fact", ["order", 1, "open"], ["order", 3, "shipped"]],
  ["fact", ["order", 2, "opne"]]]
    error 
    LogicError: Adding this fact breaks an invariant, so nothing changed. The invariant expected no answers but found 1, such as {"id":2,"status":"opne"}: ["and",["order","?id","?status"],["not",["Shelved",{"id":"?id","status":"?status"}]]]. {"id":2,"status":"opne"} does not fit "Shelved": "status" must fit ["schema/anyOf","open","shipped"] but is "opne".

    The message says which row does not fit, and where. Nothing changed: orders 1 and 3 are still on the shelf, and order 2 was not added.

    What we built

    We described an order with a schema, listed the problems of one that did not fit, named our schemas, kept the documents that fit with a rule, recorded why the others were rejected, took a list inside each order apart into rows, and guarded a relation with a schema.

    To use these features in your own project, see Check the shape of data and Take data apart. For every rule in one place, read What fits a schema and Patterns in the reference. To understand why checking and taking apart are one thing, read One set of rules for every feature.

    Run Lion from TypeScript

    Evaluate Lion programs inside your own application, give them your values and functions, and handle their results and errors.

    This guide shows how to evaluate Lion from a TypeScript or JavaScript project with @lionlang/core. It assumes you know the basics of Effect; every evaluation is an Effect you run.

    Install the package

    bun add @lionlang/core effect

    Evaluate a program

    Pass the program and an environment to run. The standard library, stdlib, is the usual environment. A program can be any JSON value, so it can come straight from JSON.parse, a database, or a request body.

    import { Effect } from "effect";
import { run } from "@lionlang/core/evaluation/evaluate";
import { stdlib } from "@lionlang/core/modules";

const program = JSON.parse('["number/add", 1, 2]');
const result = await Effect.runPromise(run(program, stdlib));
// => 3

    Give programs your own values and functions

    Spread stdlib into an object and add names. Any value can be bound. A function can return a plain value or an Effect; Lion waits for an Effect to finish.

    const env = {
  ...stdlib,
  taxRate: 0.08,
  "shop/price": (sku: string) => Effect.succeed(sku === "lamp" ? 120 : 35),
};

await Effect.runPromise(
  run(["number/multiply", ["shop/price", "lamp"], ["number/add", 1, "taxRate"]], env)
);
// => 129.6

    Prefix your names with a module, as the standard library does, so they never collide with Lion's names or with strings in your data.

    Handle errors

    A failed evaluation is a typed failure, not a thrown exception. Run with Effect.runPromiseExit, or catch by tag:

    const safe = run(["number/add", "one", 2], stdlib).pipe(
  Effect.catchTag("SchemaError", (error) => Effect.succeed(`Bad input: ${error.message}`))
);

    See Errors for every error a program can fail with.

    Keep a logic database between runs

    Each run starts with an empty logic database. To keep relations, facts, rules, and invariants across runs, create a LogicDatabase and pass it to each run:

    import { LogicDatabase } from "@lionlang/core/logic/database";

const database = new LogicDatabase();
await Effect.runPromise(run(["begin",
  ["relation", "edge", ["from", "to"]],
  ["fact", ["edge", "a", "b"]]], stdlib, { database }));

await Effect.runPromise(run(["query", ["edge", "a", "?to"]], stdlib, { database }));
// => [{ to: "b" }]

    Later runs see the database's relations by name, so they can query edge without declaring it again. Names you bind in the environment win over relations with the same name.

    Run programs from the command line

    Evaluate Lion files with the lion command, keep a logic database in a file between runs, and open the graph editor.

    This guide shows how to use the lion command from @lionlang/cli.

    Install the command

    bun add --dev @lionlang/cli

    In a project, run it with bun run lion. Installed globally, it is just lion.

    Evaluate a file

    Write a program to a JSON file and pass the file's path. The result prints as formatted JSON:

    echo '["number/add", 1, 2]' > add.json
bun run lion add.json

    If the file is not valid JSON, or the program fails, lion prints the error and exits with status 1.

    Keep a logic database in a file

    Add --database with a path. The file is loaded before the program runs and saved after it succeeds, so relations, facts, rules, and invariants carry over to the next run:

    bun run lion setup.json --database store.json
bun run lion more-facts.json --database store.json
    • A database file that does not exist yet starts empty.
    • The file is a snapshot: an ordinary Lion program, one form and one fact per line, so it diffs well in version control.
    • If the program fails, for example because it would break an invariant, the file is left as it was.
    • Running the same setup again keeps one copy of each rule and invariant.

    Open the graph editor

    bun run lion repl
bun run lion repl --host 0.0.0.0 --port 8080

    The editor listens on 127.0.0.1:3000 unless you pass --host or --port. Open the address it prints, then open a .json program.

    Branch on a value's shape

    Choose what to do with a value based on its type or its structure, with match and cond.

    This guide shows how to pick a branch based on what a value is. Use match when the choice depends on the value's type or structure, and cond when it depends on conditions you compute. The patterns of match are schemas.

    Branch on a value's type

    Give match the value, then pairs of a schema and a function, then a fallback function. A predicate is a schema: the first one that returns true picks its function, which receives the value:

    ["begin",
  ["define", "describe",
    ["lambda", ["value"],
      ["match", "value",
        ["value/number?", ["lambda", ["n"], "a number"]],
        ["value/string?", ["lambda", ["s"], ["string/concat", "a string: ", "s"]]],
        ["value/array?", ["lambda", ["xs"], "a list"]],
        ["lambda", ["other"], "something else"]]]],
  ["array/map", ["quote", [7, "hi", [1, 2], null]], "describe"]]
    result 
    ["a number","a string: hi","a list","something else"]

    Branch on a record's structure

    A record is a schema too. A record fits it when it has the same keys, with a value that fits the schema under each. A plain value fits a value equal to it, so a field can pick the branch. Records nest, and schema/open fits a record whatever other keys it has:

    ["begin",
  ["define", "route",
    ["lambda", ["message"],
      ["match", "message",
        [{"type": "order", "order": {"id": "value/number?"}},
         ["lambda", ["m"], ["object/get-path", "m", "order.id"]]],
        [{"type": ["schema/anyOf", "ping", "hello"]},
         ["lambda", ["m"], "pong"]],
        [["schema/open", {"type": "note"}],
         ["lambda", ["m"], ["object/get", "m", "text"]]],
        ["lambda", ["m"], "unknown message"]]]],
  ["array/map",
    ["quote", [
      {"type": "order", "order": {"id": 42}},
      {"type": "ping"},
      {"type": "note", "text": "call back", "from": "ada"},
      {"type": "order", "order": {"id": "x"}}]],
    "route"]]
    result 
    [42,"pong","call back","unknown message"]

    A predicate that fails, or returns something other than true, counts as no match, so a pattern never crashes on data of the wrong type. A string in a pattern is a name first, as everywhere: "order" is the string unless something is bound to order, and ["quote", "order"] is always the string.

    Branch on computed conditions

    When the choice depends on comparisons, list condition and result pairs in cond, with an optional else at the end:

    ["begin",
  ["define", "grade",
    ["lambda", ["score"],
      ["cond",
        [["number/greaterThanOrEqualTo", "score", 90], "A"],
        [["number/greaterThanOrEqualTo", "score", 75], "B"],
        ["else", "C"]]]],
  ["array/map", ["array/make", 95, 80, 40], "grade"]]
    result 
    ["A","B","C"]

    Without an else, a cond with no matching condition returns null. Conditions use JavaScript truthiness: false, null, 0, and "" do not match, and every list and record does.

    Transform lists

    Make lists, map over them, filter them, flatten them, and fold them into a single value.

    This guide shows how to work with lists using the array module and lambdas.

    Make a list

    An array in a program is a call, so [1, 2, 3] on its own fails: 1 is not a function. Make a list with array/make, which evaluates its arguments, or with quote, which takes the list as written:

    {"made": ["array/make", 1, ["number/add", 1, 1], 3],
 "quoted": ["quote", [1, ["number/add", 1, 1], 3]],
 "range": ["array/range", 0, 5]}
    result 
    {
  "made": [1,2,3],
  "quoted": [1,["number/add",1,1],3],
  "range": [0,1,2,3,4]
}

    Change every item

    Pass a list and a function to array/map:

    ["array/map", ["array/range", 1, 6],
  ["lambda", ["n"], ["number/multiply", "n", "n"]]]
    result 
    [1,4,9,16,25]

    Keep some items

    There is no filter function; use array/flat-map and return a one-item list to keep an item or an empty list to drop it:

    ["array/flat-map", ["array/range", 1, 11],
  ["lambda", ["n"],
    ["cond",
      [["number/greaterThan", "n", 6], ["array/make", "n"]],
      ["else", ["array/make"]]]]]
    result 
    [7,8,9,10]

    Combine items into one value

    array/reduce takes a list, a starting value, and a function of the running value and the next item:

    ["array/reduce", ["array/make", 3, 9, 4], 0,
  ["lambda", ["sum", "n"], ["number/add", "sum", "n"]]]
    result 
    16

    For sums, counts, and other common totals, the aggregate module is shorter: ["aggregate/sum", list].

    Take lists apart

    {"first": ["array/head", ["array/make", "a", "b", "c"]],
 "rest": ["array/tail", ["array/make", "a", "b", "c"]],
 "length": ["array/length", ["array/make", "a", "b", "c"]],
 "hasB": ["array/includes?", ["array/make", "a", "b", "c"], "b"],
 "joined": ["array/concat", ["array/make", 1], ["array/make", 2, 3]],
 "emptyFirst": ["array/head", ["array/make"]]}
    result 
    {
  "first": "a",
  "rest": ["b","c"],
  "length": 3,
  "hasB": true,
  "joined": [1,2,3],
  "emptyFirst": null
}

    The first item of an empty list is null, and the rest of it is an empty list.

    Build and run code as data

    Hold a program as data, assemble one from parts, and run it with eval.

    This guide shows how to treat Lion code as a value: keep it from running with quote, build it with ordinary functions, and run it with eval.

    Hold code without running it

    quote returns its argument exactly as written:

    ["quote", ["number/add", 1, 2]]
    result 
    ["number/add",1,2]

    Run code you hold

    eval evaluates its argument, then evaluates the result as a program:

    ["begin",
  ["define", "formula", ["quote", ["number/multiply", "price", 2]]],
  ["define", "price", 21],
  ["eval", "formula"]]
    result 
    42

    The code runs where eval is, so it sees the names defined there, including price, defined after the formula.

    Assemble a program from parts

    A program is a list, so build it with list functions. Here a list of numbers becomes a chain of additions:

    ["begin",
  ["define", "program",
    ["array/reduce", ["array/make", 2, 3, 4], 0,
      ["lambda", ["code", "n"],
        ["array/make", ["quote", "number/add"], "code", "n"]]]],
  {"program": "program", "result": ["eval", "program"]}]
    result 
    {
  "program": ["number/add",["number/add",["number/add",0,2],3],4],
  "result": 9
}

    The name is quoted because array/make evaluates its arguments: unquoted, "number/add" would become the function itself, which is not JSON, so eval would refuse the program.

    Keep programs in records

    Records evaluate their values, so quote programs you store as configuration and run the one you need:

    ["begin",
  ["define", "rules", {
    "short": ["quote", ["number/lessThan", ["string/length", "name"], 5]],
    "long": ["quote", ["number/greaterThan", ["string/length", "name"], 8]]}],
  ["define", "name", "Lion"],
  {"short": ["eval", ["object/get", "rules", "short"]],
   "long": ["eval", ["object/get", "rules", "long"]]}]
    result 
    {"short":true,"long":false}

    Query with conditions and computed values

    Narrow answers with comparisons, compute new values in rules and queries, choose between values, combine alternatives, and look inside lists.

    This guide shows how to go beyond matching facts: filter answers with conditions, compute values, accept alternatives, and match items of a list.

    Filter answers with a condition

    Call a function that answers true or false on a logic variable, and it becomes a filter. Combine goals with and:

    ["begin",
  ["relation", "order", ["id", "amount"]],
  ["fact", ["order", 1, 30], ["order", 2, 120], ["order", 3, 75]],
  ["query",
    ["and", ["order", "?id", "?amount"], ["number/greaterThan", "?amount", 50]],
    {"order": "id"}]]
    result 
    [{"id":2,"amount":120},{"id":3,"amount":75}]

    A filter runs as soon as its variables are bound, so it can come before the goal that binds them. Filters that are ready together run in the order written. When some values would make a filter fail, put a guard before it:

    ["begin",
  ["relation", "reading", ["sensor", "value"]],
  ["fact", ["reading", "s1", 21], ["reading", "s2", "offline"], ["reading", "s3", 34]],
  ["query",
    ["and", ["reading", "?sensor", "?value"],
      ["value/number?", "?value"],
      ["number/greaterThan", "?value", 30]]]]
    result 
    [{"sensor":"s3","value":34}]

    Compute a value

    Use = to bind a variable to a computed value:

    ["begin",
  ["relation", "order", ["id", "amount"]],
  ["fact", ["order", 1, 30], ["order", 2, 120]],
  ["query",
    ["and", ["order", "?id", "?amount"],
      ["=", "?withTax", ["number/multiply", "?amount", 1.25]]],
    {"order": "id"}]]
    result 
    [
  {"id":1,"amount":30,"withTax":37.5},
  {"id":2,"amount":120,"withTax":150}
]

    In a rule, a computed value can also go straight into the head:

    ["begin",
  ["relation", "user", ["id", "first", "last"]],
  ["relation", "fullName", ["id", "name"]],
  ["fact", ["user", 1, "Ada", "Lovelace"], ["user", 2, "Alan", "Turing"]],
  ["rule", ["fullName", "?id", ["string/concat", ["string/concat", "?first", " "], "?last"]],
    ["user", "?id", "?first", "?last"]],
  ["query", ["fullName", "?id", "?name"], {"order": "id"}]]
    result 
    [{"id":1,"name":"Ada Lovelace"},{"id":2,"name":"Alan Turing"}]

    Choose between values

    cond, match, and records work on logic variables too. Each waits until its variables are bound, then computes what it would with the values in place:

    ["begin",
  ["relation", "order", ["id", "amount"]],
  ["fact", ["order", 1, 30], ["order", 2, 120]],
  ["query",
    ["and", ["order", "?id", "?amount"],
      ["=", "?summary",
        {"size": ["cond", [["number/greaterThan", "?amount", 100], "large"], ["else", "small"]],
         "withTax": ["number/multiply", "?amount", 1.25]}]],
    {"order": "id"}]]
    result 
    [
  {"id":1,"amount":30,"summary":{"size":"small","withTax":37.5}},
  {"id":2,"amount":120,"summary":{"size":"large","withTax":150}}
]

    Your own lambdas work the same way, including ones that branch or call themselves:

    ["begin",
  ["define", "factorial",
    ["lambda", ["n"],
      ["cond", [["number/lessThan", "n", 2], 1],
        ["else", ["number/multiply", "n", ["factorial", ["number/subtract", "n", 1]]]]]]],
  ["query",
    ["and", ["in", "?n", ["array/range", 1, 6]], ["=", "?f", ["factorial", "?n"]]]]]
    result 
    [
  {"n":1,"f":1},
  {"n":2,"f":2},
  {"n":3,"f":6},
  {"n":4,"f":24},
  {"n":5,"f":120}
]

    Leave answers out

    not takes any goal: a relation call, a filter, or goals combined with and and or:

    ["begin",
  ["relation", "order", ["id", "amount"]],
  ["relation", "refunded", ["id"]],
  ["fact", ["order", 1, 30], ["order", 2, 120], ["order", 3, 75]],
  ["fact", ["refunded", 3]],
  ["query",
    ["and", ["order", "?id", "?amount"],
      ["not", ["or", ["refunded", "?id"], ["number/lessThan", "?amount", 50]]]]]]
    result 
    [{"id":2,"amount":120}]

    Accept alternatives

    or holds when any of its goals does:

    ["begin",
  ["relation", "order", ["id", "status"]],
  ["fact", ["order", 1, "open"], ["order", 2, "paid"], ["order", 3, "held"]],
  ["query",
    ["or", ["order", "?id", "open"], ["order", "?id", "held"]],
    {"order": "id"}]]
    result 
    [{"id":1},{"id":3}]

    Match items of a list

    When a fact holds a list, in binds a variable to each item:

    ["begin",
  ["relation", "post", ["id", "tags"]],
  ["fact",
    ["post", "p1", ["array/make", "lisp", "json"]],
    ["post", "p2", ["array/make", "json", "logic"]]],
  ["query",
    ["and", ["post", "?post", "?tags"], ["in", "json", "?tags"]],
    {"order": "post"}]]
    result 
    [
  {"post":"p1","tags":["lisp","json"]},
  {"post":"p2","tags":["json","logic"]}
]

    With an unbound first argument, in binds it to each item; with a bound one, it tests membership, as above.

    Keep goals safe

    Every variable in a filter, a computed value, or a not must be bound by a relation, =, or in somewhere in the same goal. Otherwise there would be infinitely many answers, so Lion refuses the goal and names the variable:

    ["query", ["number/greaterThan", "?amount", 50]]
    error 
    LogicError: Unsafe goal ["number/greaterThan","?amount",50]: ?amount must first be bound by a relation, "=", "in", or "schema/fits?".

    Use answers as values

    Ask the database from any expression: collect answers into a list with find, test a goal in cond, and use a relation as a predicate.

    This guide shows how to use what the database knows inside ordinary expressions, in plain code and inside rules.

    Collect answers into a list

    find takes a template and a goal, and returns the template's value for every match of the goal, sorted:

    ["begin",
  ["relation", "score", ["player", "points"]],
  ["fact", ["score", "ana", 12], ["score", "bo", 30], ["score", "cy", 30]],
  {"players": ["find", "?player", ["score", "?player", "?_"]],
   "by points": ["find", ["array/make", "?points", "?player"], ["score", "?player", "?points"]],
   "best": ["aggregate/max", ["find", "?points", ["score", "?_", "?points"]]]}]
    result 
    {
  "players": ["ana","bo","cy"],
  "by points": [[12,"ana"],[30,"bo"],[30,"cy"]],
  "best": 30
}

    The result is a plain list, so every list function works on it. Where query returns one record per answer for you to read, find returns exactly the values you ask for.

    Test a goal

    A goal is true when it has a match and false when it has none. Use it wherever a value is needed, such as a cond condition or a value of a record:

    ["begin",
  ["relation", "member", ["name", "plan"]],
  ["relation", "blocked", ["name"]],
  ["fact", ["member", "ana", "pro"], ["member", "bo", "free"]],
  ["fact", ["blocked", "bo"]],
  ["define", "access",
    ["lambda", ["who"],
      ["cond",
        [["blocked", "who"], "none"],
        [["member", "who", "pro"], "full"],
        [["member", "who", "?_"], "limited"],
        ["else", "guest"]]]],
  {"ana": ["access", "ana"],
   "bo": ["access", "bo"],
   "zed": ["access", "zed"],
   "anyone blocked": ["blocked", "?_"]}]
    result 
    {"ana":"full","bo":"none","zed":"guest","anyone blocked":true}

    A goal with a variable asks whether anything matches. Give a variable a name when the goal joins on it, as in ["and", ["member", "?m", "pro"], ["blocked", "?m"]].

    Use a relation as a predicate

    A relation is a function that builds a goal, so it works as the predicate of match and of functions that take one:

    ["begin",
  ["relation", "vowel", ["letter"]],
  ["fact", ["vowel", "a"], ["vowel", "e"], ["vowel", "i"], ["vowel", "o"], ["vowel", "u"]],
  {"flags": ["array/map", ["array/make", "l", "i", "o", "n"], "vowel"],
   "kind": ["match", "o",
     ["vowel", ["lambda", ["letter"], "a vowel"]],
     ["lambda", ["letter"], "a consonant"]]}]
    result 
    {"flags":[false,true,true,false],"kind":"a vowel"}

    Ask from inside a rule

    In a rule or query the same expressions are asked once for each answer, with the answer's variables in place. A variable that only the question mentions, such as ?child here, belongs to the question:

    ["begin",
  ["relation", "person", ["name"]],
  ["relation", "parent", ["parent", "child"]],
  ["relation", "profile", ["name", "summary"]],
  ["fact", ["person", "ada"], ["person", "ben"], ["person", "cy"]],
  ["fact", ["parent", "ada", "ben"], ["parent", "ada", "cy"]],
  ["rule",
    ["profile", "?p",
      {"children": ["find", "?child", ["parent", "?p", "?child"]],
       "kind": ["cond", [["parent", "?p", "?_"], "has children"], ["else", "no children"]]}],
    ["person", "?p"]],
  ["query", ["profile", "?name", "?summary"], {"order": "name"}]]
    result 
    [
  {
    "name": "ada",
    "summary": {"children":["ben","cy"],"kind":"has children"}
  },
  {"name":"ben","summary":{"children":[],"kind":"no children"}},
  {"name":"cy","summary":{"children":[],"kind":"no children"}}
]

    A lambda that asks works in both places, because its body is asked wherever it runs:

    ["begin",
  ["relation", "person", ["name"]],
  ["relation", "parent", ["parent", "child"]],
  ["fact", ["person", "ada"], ["person", "ben"]],
  ["fact", ["parent", "ada", "ben"], ["parent", "ada", "cy"]],
  ["define", "children", ["lambda", ["p"], ["find", "?c", ["parent", "p", "?c"]]]],
  {"in plain code": ["children", "ada"],
   "in a query":
     ["query", ["and", ["person", "?p"], ["=", "?kids", ["children", "?p"]]], {"order": "p"}]}]
    result 
    {
  "in plain code": ["ben","cy"],
  "in a query": [{"p":"ada","kids":["ben","cy"]},{"p":"ben","kids":[]}]
}

    Keep a goal as a goal

    define, and, or, not, and lambdas do not ask a goal: they keep it, so you can name goals and build bigger ones. Here the program's result is the goal itself:

    ["begin",
  ["relation", "member", ["name", "plan"]],
  ["define", "is-pro", ["member", "?who", "pro"]],
  ["and", "is-pro", ["not", ["member", "?who", "free"]]]]
    result 
    ["and",["member","?who","pro"],["not",["member","?who","free"]]]

    A goal is asked only where a value is needed. A record holds values, so it asks. To get a goal's truth on its own, give the goal to value/identity:

    ["begin",
  ["relation", "member", ["name", "plan"]],
  ["fact", ["member", "ana", "pro"]],
  ["define", "is-pro", ["member", "?who", "pro"]],
  {"in a record": "is-pro",
   "its truth": ["value/identity", "is-pro"],
   "its answers": ["query", "is-pro"]}]
    result 
    {
  "in a record": true,
  "its truth": true,
  "its answers": [{"who":"ana"}]
}

    Sort, page, and check query answers

    Order answers by one or more variables, take a page of them, and make a query fail when it finds too few or too many.

    This guide shows how to use query options, the record after a query's goal.

    Sort answers

    Give "order" a variable name, or a list of them to break ties. A leading - sorts that variable from largest to smallest:

    ["begin",
  ["relation", "score", ["player", "points"]],
  ["fact", ["score", "ana", 12], ["score", "bo", 30], ["score", "cy", 30], ["score", "dee", 7]],
  ["query", ["score", "?player", "?points"], {"order": ["-points", "player"]}]]
    result 
    [
  {"player":"bo","points":30},
  {"player":"cy","points":30},
  {"player":"ana","points":12},
  {"player":"dee","points":7}
]

    Take a page

    "offset" skips answers and "limit" caps how many come back. Sort first, so pages are stable:

    ["begin",
  ["relation", "score", ["player", "points"]],
  ["fact", ["score", "ana", 12], ["score", "bo", 30], ["score", "cy", 30], ["score", "dee", 7]],
  ["query", ["score", "?player", "?points"], {"order": "-points", "offset": 1, "limit": 2}]]
    result 
    [{"player":"cy","points":30},{"player":"ana","points":12}]

    Fail when there are no answers, or some

    "assert": "some" makes the query fail when it has no answers, and "assert": "none" when it has any. Use it to stop a program early when data is not as expected:

    ["begin",
  ["relation", "score", ["player", "points"]],
  ["fact", ["score", "ana", 12]],
  ["query", ["score", "?player", "?points"], {"assert": "none"}]]
    error 
    LogicError: The query expected no answers but found 1, such as {"player":"ana","points":12}: ["score","?player","?points"].

    The assertion sees every answer, before offset and limit. To keep a check like this in force after every change, use an invariant.

    Follow relationships of any length

    Derive paths, reachability, and hierarchies with recursive rules, and write them so queries stay fast.

    This guide shows how to follow a relationship through any number of steps, such as routes through a network or managers up an org chart.

    Write the two rules

    A path is an edge, or a path followed by an edge. Write one rule for each case:

    ["begin",
  ["relation", "edge", ["from", "to"]],
  ["relation", "path", ["from", "to"]],
  ["fact", ["edge", "a", "b"], ["edge", "b", "c"], ["edge", "c", "d"]],
  ["rule", ["path", "?x", "?y"], ["edge", "?x", "?y"]],
  ["rule", ["path", "?x", "?z"], ["path", "?x", "?y"], ["edge", "?y", "?z"]],
  ["query", ["path", "a", "?to"], {"order": "to"}]]
    result 
    [{"to":"b"},{"to":"c"},{"to":"d"}]

    Cycles are fine: evaluation stops when no new facts appear.

    Put the recursion first when you ask from a known start

    When a query gives the start, as in ["path", "a", "?to"], Lion only derives what that query can reach. Writing the recursive goal first, ["path", "?x", "?y"], ["edge", "?y", "?z"], keeps every step anchored at that start. This query along a 3,000-node chain stays fast:

    ["begin",
  ["relation", "edge", ["from", "to"]],
  ["relation", "path", ["from", "to"]],
  ["rule", ["edge", "?n", ["number/add", "?n", 1]], ["in", "?n", ["array/range", 0, 3000]]],
  ["rule", ["path", "?x", "?y"], ["edge", "?x", "?y"]],
  ["rule", ["path", "?x", "?z"], ["path", "?x", "?y"], ["edge", "?y", "?z"]],
  ["query", ["path", 2997, "?to"]]]
    result 
    [{"to":2998},{"to":2999},{"to":3000}]

    Written the other way, ["edge", "?x", "?y"], ["path", "?y", "?z"], the rule asks about every node along the way, which can cost as much as deriving every path. Goal-directed evaluation explains why.

    Carry a value along the path

    A recursive rule cannot compute a new value in its head, because that could go on forever. To carry a distance or a route, aggregate it with aggregate/min, aggregate/max, aggregate/shortest, or aggregate/union, whose values only move one way:

    ["begin",
  ["relation", "road", ["from", "to", "km"]],
  ["relation", "dist", ["to", "km"]],
  ["fact", ["road", "a", "b", 4], ["road", "a", "c", 1], ["road", "c", "b", 2], ["road", "b", "d", 5]],
  ["rule", ["dist", "?to", ["aggregate/min", "?km"]], ["road", "a", "?to", "?km"]],
  ["rule", ["dist", "?to", ["aggregate/min", ["number/add", "?d", "?km"]]],
    ["dist", "?via", "?d"], ["road", "?via", "?to", "?km"]],
  ["query", ["dist", "?to", "?km"], {"order": "km"}]]
    result 
    [{"to":"c","km":1},{"to":"b","km":3},{"to":"d","km":8}]

    For weighted shortest paths with the route itself, graph/shortestPath is simpler.

    Find what is missing

    Ask for things that have no matching fact, such as customers without orders or tasks without an owner.

    This guide shows how to use not to find what lacks something.

    Keep only what has no match

    Start from a relation that lists every candidate, then rule out the ones that have a match. ?_ stands for any value:

    ["begin",
  ["relation", "customer", ["name"]],
  ["relation", "order", ["id", "customer"]],
  ["fact", ["customer", "ana"], ["customer", "bo"], ["customer", "cy"]],
  ["fact", ["order", 1, "ana"], ["order", 2, "cy"]],
  ["query", ["and", ["customer", "?name"], ["not", ["order", "?_", "?name"]]]]]
    result 
    [{"name":"bo"}]

    Name the result with a rule

    To reuse the answer, derive it into a relation of its own:

    ["begin",
  ["relation", "task", ["id"]],
  ["relation", "owner", ["task", "person"]],
  ["relation", "unowned", ["task"]],
  ["fact", ["task", 1], ["task", 2], ["task", 3]],
  ["fact", ["owner", 2, "ana"]],
  ["rule", ["unowned", "?t"], ["task", "?t"], ["not", ["owner", "?t", "?_"]]],
  ["query", ["unowned", "?task"], {"order": "task"}]]
    result 
    [{"task":1},{"task":3}]

    Rule out a combination

    The goal under not is a question of its own, so it can join relations. A variable that appears nowhere else in the query, such as ?paper here, belongs to the question: it is not part of the answer. This finds the authors none of whose papers is cited:

    ["begin",
  ["relation", "author", ["person", "paper"]],
  ["relation", "cites", ["paper", "cited"]],
  ["fact", ["author", "ann", "p1"], ["author", "bob", "p2"], ["author", "cyd", "p3"]],
  ["fact", ["cites", "p1", "p3"], ["cites", "p3", "p1"]],
  ["query",
    ["and", ["author", "?person", "?_"],
      ["not", ["and", ["author", "?person", "?paper"], ["cites", "?_", "?paper"]]]]]]
    result 
    [{"person":"bob"}]

    Give a filter its variables

    A relation goal can find values for a variable, but a filter cannot: it needs every variable it mentions. Here nothing binds ?amount, so Lion refuses the query:

    ["begin",
  ["relation", "order", ["id", "amount"]],
  ["query", ["and", ["order", "?id", "?_"], ["not", ["number/greaterThan", "?amount", 100]]]]]
    error 
    LogicError: Unsafe goal ["not",["number/greaterThan","?amount",100]]: ?amount must first be bound by a relation, "=", "in", or "schema/fits?".

    Know what negation cannot do

    A rule cannot ask about a relation that depends on the rule's own head, directly or through other rules, because then it would have no single answer. Lion rejects such a rule when you add it. See Logic database guarantees.

    Summarize groups of facts

    Count, total, average, and collect values per group, like GROUP BY in SQL.

    This guide shows how to compute totals per group with aggregates in a rule's head.

    Group and total

    Put an aggregate such as ["aggregate/sum", "?amount"] in a column of the head. The head's other columns are the group:

    ["begin",
  ["relation", "order", ["id", "customer", "amount"]],
  ["relation", "spend", ["customer", "total", "orders"]],
  ["fact", ["order", 1, "ana", 30], ["order", 2, "ana", 20], ["order", 3, "bo", 50]],
  ["rule", ["spend", "?c", ["aggregate/sum", "?amount"], ["aggregate/count", "?id"]],
    ["order", "?id", "?c", "?amount"]],
  ["query", ["spend", "?customer", "?total", "?orders"], {"order": "customer"}]]
    result 
    [
  {"customer":"ana","total":50,"orders":2},
  {"customer":"bo","total":50,"orders":1}
]

    A group only exists when something matches, so a count is never 0; the next section reports zeros. The argument can also be a constant: ["aggregate/count", 1] counts the matches.

    Count what may be nothing

    Give the aggregate a find. It lists what a goal matches for each customer, and a list can be empty:

    ["begin",
  ["relation", "customer", ["name"]],
  ["relation", "order", ["id", "customer", "amount"]],
  ["relation", "activity", ["customer", "orders", "total"]],
  ["fact", ["customer", "ana"], ["customer", "bo"], ["customer", "cy"]],
  ["fact", ["order", 1, "ana", 30], ["order", 2, "ana", 20], ["order", 3, "bo", 50]],
  ["rule",
    ["activity", "?c",
      ["aggregate/count", ["find", "?id", ["order", "?id", "?c", "?_"]]],
      ["aggregate/sum", ["find", "?amount", ["order", "?_", "?c", "?amount"]]]],
    ["customer", "?c"]],
  ["query", ["activity", "?customer", "?orders", "?total"], {"order": "customer"}]]
    result 
    [
  {"customer":"ana","orders":2,"total":50},
  {"customer":"bo","orders":1,"total":50},
  {"customer":"cy","orders":0,"total":0}
]

    The same works without a rule, in a query or in plain code:

    ["begin",
  ["relation", "order", ["id", "customer", "amount"]],
  ["fact", ["order", 1, "ana", 30], ["order", 2, "ana", 20], ["order", 3, "bo", 50]],
  {"orders": ["aggregate/count", ["find", "?id", ["order", "?id", "?_", "?_"]]],
   "largest": ["aggregate/max", ["find", "?amount", ["order", "?_", "?_", "?amount"]]],
   "customers": ["aggregate/unique", ["find", "?c", ["order", "?_", "?c", "?_"]]]}]
    result 
    {"orders":3,"largest":50,"customers":["ana","bo"]}

    Pick the aggregate you need

    ["begin",
  ["relation", "reading", ["sensor", "n", "value"]],
  ["relation", "stats",
    ["sensor", "count", "unique", "sum", "mean", "min", "max", "values", "distinct"]],
  ["fact",
    ["reading", "s1", 1, 3], ["reading", "s1", 2, 5], ["reading", "s1", 3, 3],
    ["reading", "s2", 1, 9]],
  ["rule", ["stats", "?s",
      ["aggregate/count", "?v"], ["aggregate/countUnique", "?v"],
      ["aggregate/sum", "?v"], ["aggregate/mean", "?v"],
      ["aggregate/min", "?v"], ["aggregate/max", "?v"],
      ["aggregate/collect", "?v"], ["aggregate/unique", "?v"]],
    ["reading", "?s", "?_", "?v"]],
  ["query",
    ["stats", "?sensor", "?count", "?unique", "?sum", "?mean", "?min", "?max", "?values", "?distinct"],
    {"order": "sensor"}]]
    result 
    [
  {
    "sensor": "s1",
    "count": 3,
    "unique": 2,
    "sum": 11,
    "mean": 3.6666666666666665,
    "min": 3,
    "max": 5,
    "values": [3,3,5],
    "distinct": [3,5]
  },
  {
    "sensor": "s2",
    "count": 1,
    "unique": 1,
    "sum": 9,
    "mean": 9,
    "min": 9,
    "max": 9,
    "values": [9],
    "distinct": [9]
  }
]

    Each reading has a number, n. Facts are a set, so without it the two readings of 3 from s1 would be a single fact and would count once. Every match of a rule's body counts once, so give repeated values something that tells them apart.

    Aggregate computed values

    An aggregate can combine a computed value:

    ["begin",
  ["relation", "line", ["order", "price", "quantity"]],
  ["relation", "total", ["order", "amount"]],
  ["fact", ["line", 1, 10, 3], ["line", 1, 5, 2], ["line", 2, 8, 1]],
  ["rule", ["total", "?o", ["aggregate/sum", ["number/multiply", "?price", "?quantity"]]],
    ["line", "?o", "?price", "?quantity"]],
  ["query", ["total", "?order", "?amount"], {"order": "order"}]]
    result 
    [{"order":1,"amount":40},{"order":2,"amount":8}]

    Summarize each fact's own list

    An aggregate call combines a rule's matches only as a whole argument of the head, and only when its argument is not a find. Anywhere else, in a body or inside another call, it combines the list it is given, once for each match:

    ["begin",
  ["relation", "cart", ["id", "prices", "shipping"]],
  ["relation", "due", ["id", "amount"]],
  ["fact", ["cart", 1, ["array/make", 10, 5], 4], ["cart", 2, ["array/make", 8], 0]],
  ["rule", ["due", "?id", ["number/add", ["aggregate/sum", "?prices"], "?shipping"]],
    ["cart", "?id", "?prices", "?shipping"]],
  ["query", ["due", "?id", "?amount"], {"order": "id"}]]
    result 
    [{"id":1,"amount":19},{"id":2,"amount":8}]

    Summarize a plain list

    Outside a rule, every aggregate function combines a list right away:

    {"sum": ["aggregate/sum", ["array/make", 3, 1, 3]],
 "mean": ["aggregate/mean", ["array/make", 3, 1, 3]],
 "unique": ["aggregate/unique", ["array/make", 3, 1, 3]]}
    result 
    {"sum":7,"mean":2.3333333333333335,"unique":[1,3]}

    Answer graph questions

    Find shortest routes, rank nodes, group connected nodes, detect cycles, and order dependencies with the graph module.

    This guide shows how to run classic graph algorithms over an edge relation with the graph module. Each algorithm is called like a relation, so its rows work in queries, rules, not, and aggregates.

    Find shortest routes

    Give graph/shortestPath an edge relation and a start node, then one term each for the destination, the cost, and the path. A third edge column is the weight:

    ["begin",
  ["relation", "road", ["from", "to", "km"]],
  ["fact", ["road", "a", "b", 4], ["road", "a", "c", 1], ["road", "c", "b", 2], ["road", "b", "d", 5]],
  ["query", ["graph/shortestPath", "road", "a", "?to", "?km", "?path"]]]
    result 
    [
  {"to":"a","km":0,"path":["a"]},
  {"to":"c","km":1,"path":["a","c"]},
  {"to":"b","km":3,"path":["a","c","b"]},
  {"to":"d","km":8,"path":["a","c","b","d"]}
]

    To ask about one destination, give it as a value: ["graph/shortestPath", "road", "a", "d", "?km", "?_"]. Without a weight column, every edge costs 1.

    Start from every node a goal finds

    The start can be a variable that another goal binds. The algorithm then runs once for each start:

    ["begin",
  ["relation", "road", ["from", "to", "km"]],
  ["relation", "depot", ["at"]],
  ["fact", ["road", "a", "b", 4], ["road", "a", "c", 1], ["road", "c", "b", 2], ["road", "b", "d", 5]],
  ["fact", ["depot", "a"], ["depot", "c"]],
  ["query",
    ["and", ["depot", "?from"],
      ["graph/shortestPath", "road", "?from", "d", "?km", "?path"]],
    {"order": "from"}]]
    result 
    [
  {"from":"a","km":8,"path":["a","c","b","d"]},
  {"from":"c","km":7,"path":["c","b","d"]}
]

    Rank nodes

    ["begin",
  ["relation", "link", ["from", "to"]],
  ["fact", ["link", "a", "b"], ["link", "b", "c"], ["link", "c", "a"], ["link", "d", "c"]],
  ["query", ["graph/pageRank", "link", "?page", "?rank"], {"order": "-rank"}]]
    result 
    [
  {"page":"c","rank":0.332604},
  {"page":"a","rank":0.320214},
  {"page":"b","rank":0.309682},
  {"page":"d","rank":0.0375}
]

    Group connected nodes

    graph/components ignores edge direction; graph/stronglyConnected follows it. Groups are named after their smallest node:

    ["begin",
  ["relation", "edge", ["from", "to"]],
  ["fact", ["edge", "a", "b"], ["edge", "b", "a"], ["edge", "b", "c"], ["edge", "x", "y"]],
  {"connected": ["query", ["graph/components", "edge", "?node", "?group"], {"order": "node"}],
   "strong": ["query", ["graph/stronglyConnected", "edge", "?node", "?group"], {"order": "node"}]}]
    result 
    {
  "connected": [
    {"node":"a","group":"a"},
    {"node":"b","group":"a"},
    {"node":"c","group":"a"},
    {"node":"x","group":"x"},
    {"node":"y","group":"x"}
  ],
  "strong": [
    {"node":"a","group":"a"},
    {"node":"b","group":"a"},
    {"node":"c","group":"c"},
    {"node":"x","group":"x"},
    {"node":"y","group":"y"}
  ]
}

    Order dependencies

    graph/topologicalOrder numbers nodes so every edge points forward, or fails with an error that names a cycle:

    ["begin",
  ["relation", "before", ["first", "then"]],
  ["fact", ["before", "socks", "shoes"], ["before", "pants", "shoes"], ["before", "shirt", "tie"]],
  ["query", ["graph/topologicalOrder", "before", "?step", "?position"], {"order": "position"}]]
    result 
    [
  {"step":"pants","position":0},
  {"step":"shirt","position":1},
  {"step":"socks","position":2},
  {"step":"shoes","position":3},
  {"step":"tie","position":4}
]

    Use results in rules

    Algorithm rows can feed rules. Here, nodes far from the start are flagged:

    ["begin",
  ["relation", "road", ["from", "to", "km"]],
  ["relation", "remote", ["place"]],
  ["fact", ["road", "a", "b", 4], ["road", "a", "c", 1], ["road", "c", "b", 2], ["road", "b", "d", 5]],
  ["rule", ["remote", "?p"],
    ["graph/shortestPath", "road", "a", "?p", "?km", "?_"],
    ["number/greaterThan", "?km", 5]],
  ["query", ["remote", "?place"]]]
    result 
    [{"place":"d"}]

    An algorithm runs once its input relation is complete, the first time a goal asks for its rows. So it cannot be part of a recursive cycle, and its relation cannot have facts or rules of its own.

    Enforce rules on your data

    State conditions your data must always meet, and have the database refuse any change that would break them.

    This guide shows how to keep a logic database consistent with invariants. An invariant is a query assertion the database keeps: after every change, it asks the question again, and a change that breaks the answer is refused.

    Forbid a situation

    Write a goal that describes the bad situation, and assert it has "none" answers:

    ["begin",
  ["relation", "order", ["id", "status"], {"key": "id"}],
  ["relation", "cancelled", ["id"]],
  ["fact", ["order", 1, "open"], ["order", 2, "shipped"]],
  ["invariant",
    ["and", ["order", "?id", "shipped"], ["cancelled", "?id"]],
    {"assert": "none"}],
  ["fact", ["cancelled", 2]]]
    error 
    LogicError: Adding this fact breaks an invariant, so nothing changed. The invariant expected no answers but found 1, such as {"id":2}: ["and",["order","?id","shipped"],["cancelled","?id"]].

    The error names the invariant and one answer that breaks it, here order 2.

    Require something to exist

    Assert "some" to require at least one answer at all times, such as at least one admin:

    ["begin",
  ["relation", "role", ["user", "name"]],
  ["fact", ["role", "ana", "admin"], ["role", "bo", "admin"]],
  ["invariant", ["role", "?_", "admin"], {"assert": "some"}],
  ["retract", ["role", "ana", "admin"]],
  ["retract", ["role", "bo", "admin"]]]
    error 
    LogicError: Retracting this fact breaks an invariant, so nothing changed. The invariant expected at least one answer but found none: ["role","?_","admin"].

    Retracting Ana's role is fine; retracting the last admin is refused.

    Check derived data

    An invariant can ask anything a query can, including relations that rules derive, not, aggregates, and graph algorithms. Here no customer may owe more than 100:

    ["begin",
  ["relation", "order", ["id", "customer", "amount"]],
  ["relation", "owed", ["customer", "total"]],
  ["rule", ["owed", "?c", ["aggregate/sum", "?a"]], ["order", "?_", "?c", "?a"]],
  ["invariant",
    ["and", ["owed", "?c", "?total"], ["number/greaterThan", "?total", 100]],
    {"assert": "none"}],
  ["fact", ["order", 1, "ana", 60]],
  ["fact", ["order", 2, "ana", 50]]]
    error 
    LogicError: Adding this fact breaks an invariant, so nothing changed. The invariant expected no answers but found 1, such as {"c":"ana","total":110}: ["and",["owed","?c","?total"],["number/greaterThan","?total",100]].

    Make changes that only hold together

    Each fact, retract, or rule form is checked once it has made all of its changes. Put changes that only satisfy the invariants together in one form:

    ["begin",
  ["relation", "employee", ["name"]],
  ["relation", "manager", ["employee", "manager"], {"key": "employee"}],
  ["invariant",
    ["and", ["employee", "?e"], ["not", ["manager", "?e", "?_"]], ["not", ["manager", "?_", "?e"]]],
    {"assert": "none"}],
  ["fact", ["employee", "ana"], ["employee", "bo"], ["manager", "bo", "ana"]],
  ["query", ["manager", "?employee", "?manager"]]]
    result 
    [{"employee":"bo","manager":"ana"}]

    Separate forms in a begin are separate changes, each checked on its own.

    Check the shape of each row

    A condition on a single row, such as "the status is one of these", is a schema. The relation option "schema" keeps it as an invariant for you; see Check the shape of data. Checking a write costs what its new rows cost: an invariant is asked again only after a change to a relation it reads, and one that says no row of a relation fails a test is asked about the new rows alone. An invariant that calls a function from the host is asked in full every time, unless the function says it reads only its arguments.

    ["begin",
  ["schema", "Order",
    ["schema/open", {"id": "value/integer?", "status": ["schema/anyOf", "open", "paid", "shipped"]}]],
  ["relation", "order", ["id", "customer", "status"], {"key": "id", "schema": "Order"}],
  ["fact", ["order", 1, "ana", "open"]],
  ["fact", ["order", 2, "bo", "lost"]]]
    error 
    LogicError: Adding this fact breaks an invariant, so nothing changed. The invariant expected no answers but found 1, such as {"id":2,"customer":"bo","status":"lost"}: ["and",["order","?id","?customer","?status"],["not",["Order",{"id":"?id","customer":"?customer","status":"?status"}]]]. {"id":2,"customer":"bo","status":"lost"} does not fit "Order": "status" must fit ["schema/anyOf","open","paid","shipped"] but is "lost".

    Keep invariants across runs

    Invariants live in the database, so they persist wherever it does: in a shared LogicDatabase from TypeScript, and in a --database file on the command line. Snapshots save them, and running a setup again adds no second copy.

    Check the shape of data

    Say what a value must be with a schema, find where data does not fit, and have a relation refuse rows that do not.

    This guide shows how to check data against a schema. A schema says what a value must be, and Lion has one rule for what fits one: a function is a predicate, a record or list fits part by part, and any other value fits a value equal to it.

    Describe a record

    Write the record you expect, with a schema in place of each value. schema/fits? asks whether a value fits, and schema/problems lists every place where it does not:

    ["begin",
  ["define", "Order",
    {"id": "value/integer?",
     "status": ["schema/anyOf", "open", "shipped"],
     "note": ["schema/optional", "value/string?"]}],
  ["define", "incoming", ["quote", {"id": "7", "status": "opne"}]],
  {"fits": ["schema/fits?", "incoming", "Order"],
   "problems": ["schema/problems", "incoming", "Order"]}]
    result 
    {
  "fits": false,
  "problems": [
    {"path":["id"],"expected":"value/integer?","found":"7"},
    {
      "path": ["status"],
      "expected": ["schema/anyOf","open","shipped"],
      "found": "opne"
    }
  ]
}

    Each problem has the path to the part that does not fit, the schema that was expected there, and the value that was found. A record schema fits a record with the same keys, so a key it does not name is a problem too, with only what was found. Wrap the record in schema/open to allow other keys.

    Allow keys you do not name

    A record schema says every key the record has. To check some keys and let the rest be, wrap the record in schema/open. To let one key be left out, give it schema/optional:

    ["begin",
  ["define", "incoming", ["quote", {"id": 7, "status": "open", "rush": true}]],
  {"exact": ["schema/problems", "incoming",
     {"id": "value/integer?", "status": "value/string?"}],
   "open": ["schema/fits?", "incoming",
     ["schema/open", {"id": "value/integer?", "status": "value/string?"}]],
   "optional": ["schema/fits?", "incoming",
     {"id": "value/integer?", "status": "value/string?",
      "rush": ["schema/optional", "value/boolean?"],
      "note": ["schema/optional", "value/string?"]}]}]
    result 
    {
  "exact": [{"path":["rush"],"found":true}],
  "open": true,
  "optional": true
}

    Check lists and plain values

    A list of schemas fits a list of the same length, item by item, which suits a pair or a triple. schema/arrayOf fits a list of any length whose items all fit, and schema/recordOf a record whose values all fit. Any value that is not a function, a record, or a list fits a value equal to it, so data is a schema for itself:

    {"a pair": ["schema/fits?",
   ["array/make", 2, "kg"],
   ["array/make", "value/number?", ["schema/anyOf", "kg", "lb"]]],
 "a longer list": ["schema/fits?",
   ["array/make", 2, "kg", "net"],
   ["array/make", "value/number?", "value/string?"]],
 "every item": ["schema/fits?", ["array/make", 1, 2, 3], ["schema/arrayOf", "value/integer?"]],
 "every value": ["schema/problems", {"tea": 2, "cup": "one"}, ["schema/recordOf", "value/integer?"]],
 "the same data": ["schema/fits?", ["quote", {"a": [1, 2]}], ["quote", {"a": [1, 2]}]]}
    result 
    {
  "a pair": true,
  "a longer list": false,
  "every item": true,
  "every value": [{"path":["cup"],"expected":"value/integer?","found":"one"}],
  "the same data": true
}

    Give a schema a name

    schema declares a schema under a name, the way relation declares a relation. The name is then a predicate, and other schemas can use it. A shape can name its own schema, which describes nested data, and one form can declare several schemas that name each other:

    ["begin",
  ["schema", "Line",
    {"sku": "value/string?",
     "qty": ["schema/allOf", "value/integer?",
       ["lambda", ["n"], ["number/greaterThan", "n", 0]]]}],
  ["schema", "Order", {"id": "value/integer?", "lines": ["schema/arrayOf", "Line"]}],
  ["schema", "Folder", {"name": "value/string?", "folders": ["schema/arrayOf", "Folder"]}],
  ["schema",
    "Expr", ["schema/anyOf", "value/number?", "Sum"],
    "Sum", {"add": ["schema/arrayOf", "Expr"]}],
  {"order": ["Order", ["quote", {"id": 1, "lines": [{"sku": "a1", "qty": 2}]}]],
   "expr": ["Expr", ["quote", {"add": [1, {"add": [2, 3]}]}]],
   "bad line": ["schema/problems",
     ["quote", {"id": 1, "lines": [{"sku": "a1", "qty": 0}]}], "Order"],
   "folder": ["Folder",
     ["quote", {"name": "root", "folders": [{"name": "src", "folders": []}]}]]}]
    result 
    {
  "order": true,
  "expr": true,
  "bad line": [
    {
      "path": ["lines",0,"qty"],
      "expected": ["lambda",["n"],["number/greaterThan","n",0]],
      "found": 0
    }
  ],
  "folder": true
}

    A lambda is a schema for whatever it returns true for. One that fails, as number/greaterThan does on a string, simply does not fit. A misspelled name is different: "value/intger?" in a shape is an error that suggests value/integer?, and not a schema that nothing fits.

    Stop on data that does not fit

    schema/assert returns the value when it fits, so it can wrap the place where data comes in. When the value does not fit, it fails and says where:

    ["begin",
  ["schema", "Order", {"id": "value/integer?", "status": ["schema/anyOf", "open", "shipped"]}],
  ["object/get",
    ["schema/assert", ["quote", {"id": 7, "status": "opne"}], "Order"],
    "id"]]
    error 
    LogicError: {"id":7,"status":"opne"} does not fit "Order": "status" must fit ["schema/anyOf","open","shipped"] but is "opne".

    Sort incoming data with rules

    A schema check is a call like any other, so it works as a goal in a rule, under not, and in a find. Here raw documents go in as facts. One rule keeps the ones that fit, and takes them apart with a pattern, and another turns each problem of the others into a row:

    ["begin",
  ["relation", "inbox", ["doc"]],
  ["relation", "order", ["id", "status"], {"key": "id"}],
  ["relation", "rejected", ["doc", "where"]],
  ["schema", "Order", {"id": "value/integer?", "status": ["schema/anyOf", "open", "shipped"]}],
  ["fact",
    ["inbox", {"id": 1, "status": "open"}],
    ["inbox", {"id": 2, "status": "opne"}],
    ["inbox", {"id": "3", "status": "shipped"}]],
  ["rule", ["order", "?id", "?status"],
    ["inbox", ["schema/allOf", "Order", {"id": "?id", "status": "?status"}]]],
  ["rule", ["rejected", "?doc", ["object/get", "?problem", "path"]],
    ["inbox", "?doc"], ["in", "?problem", ["schema/problems", "?doc", "Order"]]],
  {"orders": ["query", ["order", "?id", "?status"]],
   "rejected": ["query", ["rejected", "?doc", "?where"], {"order": "where"}],
   "how many": ["aggregate/count",
     ["find", "?doc", ["and", ["inbox", "?doc"], ["not", ["Order", "?doc"]]]]]}]
    result 
    {
  "orders": [{"id":1,"status":"open"}],
  "rejected": [
    {"doc":{"id":"3","status":"shipped"},"where":["id"]},
    {"doc":{"id":2,"status":"opne"},"where":["status"]}
  ],
  "how many": 2
}

    Have a relation refuse rows that do not fit

    The relation option "schema" names a declared schema that every row must fit. A row is checked as a record of its columns, so the schema names every column, or is a schema/open record that names some. A fact form that would add a row that does not fit fails, and changes nothing:

    ["begin",
  ["schema", "Order", {"id": "value/integer?", "status": ["schema/anyOf", "open", "shipped"]}],
  ["relation", "order", ["id", "status"], {"key": "id", "schema": "Order"}],
  ["fact", ["order", 1, "open"]],
  ["fact", ["order", 2, "opne"]]]
    error 
    LogicError: Adding this fact breaks an invariant, so nothing changed. The invariant expected no answers but found 1, such as {"id":2,"status":"opne"}: ["and",["order","?id","?status"],["not",["Order",{"id":"?id","status":"?status"}]]]. {"id":2,"status":"opne"} does not fit "Order": "status" must fit ["schema/anyOf","open","shipped"] but is "opne".

    The option stands for the invariant that the message shows, so it is kept like every invariant, and the message ends with where the row does not fit.

    Require that a value exists elsewhere

    A relation with one column is a predicate, so it is a schema: a value fits person when it is one of its rows. As the schema of a column, that is a foreign key. Retracting a person who is still someone's parent is refused:

    ["begin",
  ["relation", "person", ["name"]],
  ["schema", "Kin", {"parent": "person", "child": "person"}],
  ["relation", "parent", ["parent", "child"], {"schema": "Kin"}],
  ["fact", ["person", "ada"], ["person", "ben"], ["parent", "ada", "ben"]],
  ["retract", ["person", "ben"]]]
    error 
    LogicError: Retracting this fact breaks an invariant, so nothing changed. The invariant expected no answers but found 1, such as {"parent":"ada","child":"ben"}: ["and",["parent","?parent","?child"],["not",["Kin",{"parent":"?parent","child":"?child"}]]]. {"parent":"ada","child":"ben"} does not fit "Kin": "child" must fit "person" but is "ben".

    One fact form can add a person and their parent together, since a form is checked once it has made all of its changes.

    Check data from TypeScript

    Bind the data to a name in the environment, and check it against a schema the database holds:

    import { run } from "@lionlang/core/evaluation/evaluate";
import { LogicDatabase } from "@lionlang/core/logic/database";
import { stdlib } from "@lionlang/core/modules";
import { Effect } from "effect";

const database = new LogicDatabase();
await Effect.runPromise(
  run(["schema", "Order", { id: "value/integer?" }], stdlib, { database })
);

const problems = await Effect.runPromise(
  run(["schema/problems", "incoming", "Order"], { ...stdlib, incoming }, { database })
);

    An empty list means incoming fits. Schemas are data like the rest of a Lion program, so a program can add them while it runs, and a snapshot saves the ones a database holds.

    Take data apart

    Bind logic variables to the parts of records and lists with patterns, in relation calls, queries, and rules.

    This guide shows how to get at the parts of nested data in a rule or query. A schema with a logic variable in it is a pattern: the variable takes the value it meets, so one goal checks a value and takes it apart.

    Bind the fields of a record

    Write the record you are looking for as an argument of a relation call, with a variable where a value should go. The call asks for the rows that fit, and binds the variables:

    ["begin",
  ["relation", "inbox", ["doc"]],
  ["fact",
    ["inbox", {"type": "refund", "id": 3}],
    ["inbox", {"type": "refund", "id": 4}],
    ["inbox", {"type": "order", "id": 1}]],
  ["query", ["inbox", {"type": "refund", "id": "?id"}], {"order": "id"}]]
    result 
    [{"id":3},{"id":4}]

    A record in a pattern fits a record with the same keys. The value "refund" fits only itself, so it picks the rows, and ?id takes the id of each.

    Take some keys of a larger record

    schema/open fits a record whatever other keys it has, so a pattern can name only the keys it needs. ?_ fits any value and binds nothing, which asks only that a key is there:

    ["begin",
  ["relation", "inbox", ["doc"]],
  ["fact",
    ["inbox", {"type": "order", "id": 1, "note": "gift"}],
    ["inbox", {"type": "order", "id": 2, "rush": true}],
    ["inbox", {"type": "refund", "id": 3}]],
  {"orders": ["find", "?id", ["inbox", ["schema/open", {"type": "order", "id": "?id"}]]],
   "with a note": ["find", "?id", ["inbox", ["schema/open", {"id": "?id", "note": "?_"}]]]}]
    result 
    {"orders":[1,2],"with a note":[1]}

    Go through a list inside a record

    The element of in can be a pattern too. Here one goal takes the lines out of each order, and in takes each line apart, so a rule turns nested documents into rows that other rules can count:

    ["begin",
  ["relation", "inbox", ["doc"]],
  ["relation", "line", ["order", "sku", "qty"]],
  ["relation", "units", ["order", "total"]],
  ["fact",
    ["inbox", ["quote", {"id": 1, "lines": [{"sku": "a1", "qty": 2}, {"sku": "b2", "qty": 1}]}]],
    ["inbox", ["quote", {"id": 2, "lines": [{"sku": "a1", "qty": 5}]}]]],
  ["rule", ["line", "?order", "?sku", "?qty"],
    ["inbox", {"id": "?order", "lines": "?lines"}],
    ["in", {"sku": "?sku", "qty": "?qty"}, "?lines"]],
  ["rule", ["units", "?order", ["aggregate/sum", "?qty"]],
    ["line", "?order", "?sku", "?qty"]],
  {"lines": ["find", ["array/make", "?order", "?sku", "?qty"], ["line", "?order", "?sku", "?qty"]],
   "units": ["query", ["units", "?order", "?total"], {"order": "order"}]}]
    result 
    {
  "lines": [[1,"a1",2],[1,"b2",1],[2,"a1",5]],
  "units": [{"order":1,"total":3},{"order":2,"total":5}]
}

    Take a list apart by position

    A list of variables fits a list of the same length. = matches one side against the other, so it binds the variables on either side:

    ["begin",
  ["relation", "route", ["stops"]],
  ["fact",
    ["route", ["array/make", "oslo", "bergen", "voss"]],
    ["route", ["array/make", "rome", "pisa", "turin"]],
    ["route", ["array/make", "kyoto", "nara"]]],
  ["query",
    ["and", ["route", "?stops"], ["=", ["array/make", "?from", "?_", "?to"], "?stops"]],
    {"order": "from"}]]
    result 
    [
  {"stops":["oslo","bergen","voss"],"from":"oslo","to":"voss"},
  {"stops":["rome","pisa","turin"],"from":"rome","to":"turin"}
]

    The route with two stops has no answer, since the pattern has three places.

    Check a part while you take it

    Every schema works in a pattern. A predicate says what a part must be, schema/allOf checks a part and binds it, and schema/anyOf offers a choice. A predicate can be made from a variable that another goal binds:

    ["begin",
  ["relation", "reading", ["sensor", "celsius"]],
  ["relation", "limit", ["celsius"]],
  ["fact",
    ["reading", "attic", 30], ["reading", "cellar", 10], ["reading", "roof", "n/a"],
    ["limit", 25]],
  {"numbers": ["find", "?sensor", ["reading", "?sensor", "value/number?"]],
   "hot": ["find", "?sensor",
     ["and", ["limit", "?max"],
       ["reading", "?sensor", ["func/partial", "number/lessThan", "?max"]]]],

     ["reading", ["schema/anyOf", "attic", "roof"], "?celsius"]],

     {"order": "sensor"}]}]
    result

    Take apart a value you already have

    schema/fits? is the same goal for a value that another goal bound, or one from outside. With a named schema and a pattern in one schema/allOf, a rule keeps the documents that fit and takes them apart at once:

    ["begin",
  ["relation", "inbox", ["doc"]],
  ["relation", "order", ["id", "status"], {"key": "id"}],
  ["schema", "Order", {"id": "value/integer?", "status": ["schema/anyOf", "open", "shipped"]}],

    ["inbox", {"id": 1, "status": "open"}],

    ["inbox", ["schema/allOf", "Order", {"id": "?id", "status": "?status"}]]],
  {"orders": ["query", ["order", "?id", "?status"]],
   "one value": ["query",

}

    Explain a result

    Find out why a fact holds: which rule derived it, from which facts, all the way down.

    This guide shows how to use why to trace a derived fact back to its sources.

    Ask why a fact holds

    Give why the fact, with no variables:

    ["begin",
  ["relation", "edge", ["from", "to"]],
  ["relation", "path", ["from", "to"]],
  ["fact", ["edge", "a", "b"], ["edge", "b", "c"]],
  ["rule", ["path", "?x", "?y"], ["edge", "?x", "?y"]],
  ["rule", ["path", "?x", "?z"], ["path", "?x", "?y"], ["edge", "?y", "?z"]],
  ["why", ["path", "a", "c"]]]
    result 
    {
  "fact": ["path","a","c"],
  "rule": [
    "rule",
    ["path","?x","?z"],
    ["path","?x","?y"],
    ["edge","?y","?z"]
  ],
  "because": [
    {
      "fact": ["path","a","b"],
      "rule": ["rule",["path","?x","?y"],["edge","?x","?y"]],
      "because": [{"fact":["edge","a","b"],"given":true}]
    },
    {"fact":["edge","b","c"],"given":true}
  ]
}

    Each level names the fact, the rule that derived it, and the facts because of which it holds. A fact you added says "given": true.

    Read filters and negations

    Filters appear as check, with the values they were called on, and negations as absent, with the pattern that had no match:

    ["begin",
  ["relation", "user", ["name", "age"]],
  ["relation", "banned", ["name"]],
  ["relation", "eligible", ["name"]],
  ["fact", ["user", "ana", 34]],
  ["rule", ["eligible", "?n"],
    ["user", "?n", "?age"],
    ["number/greaterThan", "?age", 18],
    ["not", ["banned", "?n"]]],
  ["why", ["eligible", "ana"]]]
    result 
    {
  "fact": ["eligible","ana"],
  "rule": [
    "rule",
    ["eligible","?n"],
    ["user","?n","?age"],
    ["number/greaterThan","?age",18],
    ["not",["banned","?n"]]
  ],
  "because": [
    {"fact":["user","ana",34],"given":true},
    {"check":["number/greaterThan",34,18]},
    {"absent":["banned","ana"]}
  ]
}

    See what a pattern matched

    A goal can say which rows it wants with a pattern or a schema, and then the goal itself does not say which row it found. why does: the premise is the row the goal matched. A schema check that held is a check:

    ["begin",
  ["relation", "inbox", ["doc"]],
  ["relation", "big", ["id"]],
  ["schema", "Order", ["schema/open", {"id": "value/integer?"}]],
  ["fact",
    ["inbox", {"id": 1, "total": 80, "note": "gift"}],
    ["inbox", {"id": 2, "total": 20}]],
  ["rule", ["big", "?id"],
    ["inbox", ["schema/open", {"id": "?id", "total": "?total"}]],
    ["schema/fits?", {"id": "?id"}, "Order"],
    ["number/greaterThan", "?total", 50]],
  ["why", ["big", 1]]]
    result 
    {
  "fact": ["big",1],
  "rule": [
    "rule",
    ["big","?id"],
    ["inbox",["schema/open",{"id":"?id","total":"?total"}]],
    ["schema/fits?",{"id":"?id"},"Order"],
    ["number/greaterThan","?total",50]
  ],
  "because": [
    {
      "fact": ["inbox",{"id":1,"total":80,"note":"gift"}],
      "given": true
    },
    {"check":["schema/fits?",{"id":1},"Order"]},
    {"check":["number/greaterThan",80,50]}
  ]
}

    See what an aggregate combined

    For an aggregated fact, why lists every match it combined under matches. For min, max, and shortest, it explains the one match that produced the value.

    ["begin",
  ["relation", "order", ["id", "customer", "amount"]],
  ["relation", "spend", ["customer", "total"]],
  ["fact", ["order", 1, "ana", 30], ["order", 2, "ana", 20]],
  ["rule", ["spend", "?c", ["aggregate/sum", "?a"]], ["order", "?_", "?c", "?a"]],
  ["why", ["spend", "ana", 50]]]
    result 
    {
  "fact": ["spend","ana",50],
  "rule": [
    "rule",
    ["spend","?c",["aggregate/sum","?a"]],
    ["order","?_","?c","?a"]
  ],
  "matches": [
    [{"fact":["order",1,"ana",30],"given":true}],
    [{"fact":["order",2,"ana",20],"given":true}]
  ]
}

    Handle facts that do not hold

    why returns null when the fact does not hold, so you can test the result:

    ["begin",
  ["relation", "edge", ["from", "to"]],
  ["fact", ["edge", "a", "b"]],
  ["why", ["edge", "b", "a"]]]
    result 
    null

    Save and load a logic database

    Write a database out as a Lion program, store it anywhere, and rebuild it later from the command line or TypeScript.

    This guide shows how to persist a logic database. A saved database is a snapshot: an ordinary Lion program of relation, schema, fact, rule, and invariant forms that rebuilds it when run.

    Take a snapshot in Lion

    ["begin",
  ["relation", "edge", ["from", "to"]],
  ["relation", "path", ["from", "to"]],
  ["fact", ["edge", "a", "b"], ["edge", "b", "c"]],
  ["rule", ["path", "?x", "?y"], ["edge", "?x", "?y"]],
  ["invariant", ["edge", "?x", "?x"], {"assert": "none"}],
  ["snapshot"]]
    result 
    [
  "begin",
  ["relation","edge",["from","to"]],
  ["relation","path",["from","to"]],
  ["fact",["edge","a","b"],["edge","b","c"]],
  ["rule",["path","?x","?y"],["edge","?x","?y"]],
  ["invariant",["edge","?x","?x"],{"assert":"none"}]
]

    Strings that would load as something else, such as relation names, logic variable names, and namespaced names, are written inside quote, and so are lists and records. Rules are written with values as they were evaluated. A named schema is written with its shape, schemas that one form declared in one form, and the schema of a relation's rows as the invariant it stands for.

    Save schemas with the data

    A database holds its schemas too, so a snapshot writes them. Schemas that one form declared are written in one form, a rule keeps the pattern it was written with, and the schema of a relation's rows is written as the invariant it stands for, so a loaded database refuses the same rows:

    ["begin",
  ["schema",
    "Expr", ["schema/anyOf", "value/number?", "Sum"],
    "Sum", {"add": ["schema/arrayOf", "Expr"]}],
  ["schema", "Order", ["schema/open", {"id": "value/integer?", "total": "Expr"}]],
  ["relation", "order", ["id", "total", "note"], {"key": "id", "schema": "Order"}],
  ["relation", "summed", ["id"]],
  ["fact", ["order", 1, ["quote", {"add": [2, 3]}], "gift"]],
  ["rule", ["summed", "?id"], ["order", "?id", {"add": "?parts"}, "?_"]],
  ["snapshot"]]
    result 
    [
  "begin",
  ["relation","order",["id","total","note"],{"key":["id"]}],
  ["relation","summed",["id"]],
  [
    "schema",
    "Expr",
    ["schema/anyOf","value/number?","Sum"],
    "Sum",
    {"add":["schema/arrayOf","Expr"]}
  ],
  [
    "schema",
    "Order",
    ["schema/open",{"id":"value/integer?","total":"Expr"}]
  ],
  ["fact",["order",1,["quote",{"add":[2,3]}],"gift"]],
  [
    "rule",
    ["summed","?id"],
    ["order","?id",{"add":"?parts"},"?_"]
  ],
  [
    "invariant",
    [
      "and",
      ["order","?id","?total","?note"],
      [
        "not",
        ["Order",{"id":"?id","total":"?total","note":"?note"}]
      ]
    ],
    {"assert":"none"}
  ]
]

    Restore facts from a snapshot

    A snapshot is a program, so evaluating it puts back what it holds. Here a fact is removed after the snapshot, and running the snapshot with eval restores it:

    ["begin",
  ["relation", "edge", ["from", "to"]],
  ["fact", ["edge", "a", "b"], ["edge", "b", "c"]],
  ["define", "saved", ["snapshot"]],
  ["retract", ["edge", "a", "b"]],
  {"before": ["query", ["edge", "?from", "?to"]],
   "restored": ["begin", ["eval", "saved"], ["query", ["edge", "?from", "?to"]]]}]
    result 
    {
  "before": [{"from":"b","to":"c"}],
  "restored": [{"from":"b","to":"c"},{"from":"a","to":"b"}]
}

    Evaluating a snapshot adds to the database; it does not remove facts the snapshot lacks. To start over, load it into an empty database.

    Save and load from TypeScript

    saveDatabase and loadDatabase do the same with a LogicDatabase:

    import { readFileSync, writeFileSync } from "node:fs";
import { Effect } from "effect";
import { run } from "@lionlang/core/evaluation/evaluate";
import { loadDatabase, saveDatabase } from "@lionlang/core/logic/snapshot";
import { stdlib } from "@lionlang/core/modules";

const program = Effect.gen(function* () {
  const database = yield* loadDatabase(JSON.parse(readFileSync("store.json", "utf8")), stdlib);
  yield* run(["fact", ["edge", "c", "d"]], stdlib, { database });
  writeFileSync("store.json", JSON.stringify(yield* saveDatabase(database)));
});

    A rule is saved with everything it holds: a function under the name the environment gives it, and a cond, record, or lambda that waits for a logic variable as its own form. Two things have no written form, a lambda that calls itself and a function made while the program ran, and saveDatabase fails with an error that names them.

    Save from the command line

    bun run lion program.json --database store.json

    The command loads store.json, runs the program against it, and saves it back one form and one fact per line, unless the program fails.

    Add your own functions and algorithms

    Give Lion programs your own values and functions, use them inside logic rules, and add graph-style algorithms.

    This guide shows how to extend the environment from TypeScript. It assumes you can already run Lion from TypeScript.

    Add a function

    Bind a function under a namespaced name. It receives evaluated arguments and returns a plain value or an Effect:

    import { Effect } from "effect";
import { run } from "@lionlang/core/evaluation/evaluate";
import { stdlib } from "@lionlang/core/modules";

const env = {
  ...stdlib,
  "text/upper": (text: string) => text.toUpperCase(),
  "shop/stock": (sku: string) => Effect.promise(() => fetchStock(sku)),
};

await Effect.runPromise(run(["text/upper", "lion"], env)); // => "LION"

    Return an Effect for anything asynchronous or anything that can fail, so Lion can wait for it and report failures as typed errors.

    Add a module of functions

    namespaceEntries prefixes every key of a record, the way the standard library is built:

    import { namespaceEntries, stdlib } from "@lionlang/core/modules";

const text = {
  upper: (s: string) => s.toUpperCase(),
  lower: (s: string) => s.toLowerCase(),
};

const env = { ...stdlib, ...namespaceEntries("text", text) };
// "text/upper" and "text/lower"

    Use functions inside rules

    A host function needs nothing more to work in a rule or query. Like every function, it waits when it is called with a logic variable, and runs once the variable is bound, so it works as a filter or a computed value:

    const text = {
  upper: (s: string) => s.toUpperCase(),
  "long?": (s: string) => s.length > 8,
};

const env = { ...stdlib, ...namespaceEntries("text", text) };
// ["rule", ["shout", "?n", ["text/upper", "?n"]], ["name", "?n"], ["text/long?", "?n"]]

    Use functions that return the same result for the same arguments and have no side effects; the engine may call them any number of times, in any order. A function used as a filter must return true or false.

    A goal given to your function is asked first, so the function receives true or false.

    A string of the form module/name that nothing is bound to is an error when its module has other names, so a program that misspells one of your functions is told which name it probably meant.

    Use a function as a schema

    A function is a predicate, so a function you add is a schema for the values it returns true for. It works wherever a schema does: in schema/fits?, in match, as a part of a record, and as an argument of a relation call. To check a value against a schema from your own code, use fits:

    import { Effect } from "effect";
import { fits } from "@lionlang/core/logic/fit";

const env = {
  ...stdlib,
  "text/email?": (value: unknown) => typeof value === "string" && value.includes("@"),
  "list/count": (items: unknown[], schema: unknown) =>
    Effect.map(
      Effect.filter(items, (item) =>
        Effect.map(fits(schema, item), (fit) => fit === true)
      ),
      (kept) => kept.length
    ),
};
// ["schema/fits?", {"to": "ada@example.com"}, {"to": "text/email?"}]
// ["query", ["contact", "?name", "text/email?"]]
// ["list/count", "rows", {"to": "text/email?"}]

    Tell Lion what a function reads

    An invariant is asked again only when a change can have broken it, which takes knowing what its goal reads. Lion cannot see inside your function: it might read the database on its own. So an invariant whose goal calls a host function, in the goal itself, inside a schema, or through a rule, is asked in full after every change to facts. That is always correct, and costs more on a large database. A function that reads nothing but its arguments can say so:

    import { readsOnlyArguments } from "@lionlang/core/logic/terms";

const isEmail = (value: unknown) => typeof value === "string" && value.includes("@");
readsOnlyArguments({ isEmail });

const env = { ...stdlib, "text/email?": isEmail };
// ["invariant", ["and", ["contact", "?name", "?to"], ["not", ["text/email?", "?to"]]], {"assert": "none"}]

    The invariant is then treated like one over the standard library: a change to contact checks the new rows, and a change to any other relation does not ask it at all.

    Call back into Lion

    A function that takes a Lion function, such as a lambda or a relation, calls it with call. It gives the callback's value, with a goal asked, and lets the whole call wait when that value is not known yet:

    import { Effect } from "effect";
import { call } from "@lionlang/core/evaluation/special-forms/function";

const env = {
  ...stdlib,
  "list/keep": (items: unknown[], keep: unknown) =>
    Effect.filter(items, (item) =>
      Effect.map(call(keep, item), (kept) => kept === true)
    ),
};
// ["list/keep", ["array/make", "ana", "bo"], "member"]
// ["rule", ["shortlist", ["list/keep", "?names", "member"]], ["team", "?names"]]

    Build goals from host code

    A function that should receive logic variables as they are, to build a goal from them, is marked with logicFunction:

    import { LogicForm, logicFunction } from "@lionlang/core/logic/terms";

const same = logicFunction((left: unknown, right: unknown) =>
  Effect.succeed(new LogicForm("=", [left, right]))
);

const env = { ...stdlib, "my/same": same };
// ["query", ["and", ["name", "?n"], ["my/same", "?shout", ["text/upper", "?n"]]]]

    Add an algorithm

    For work that rules do badly, defineAlgorithm turns a function over whole relations into a goal, like those in the graph module. It receives each relation input as its tuples and each value input as itself, and returns rows, or a string that explains why it cannot. A value input can be a variable that another goal binds; the function then runs once for each value. An input must be JSON data. The columns the function returns are matched like a relation's, so a goal can give a schema for one:

    import { defineAlgorithm } from "@lionlang/core/logic/algorithms";

const outDegree = defineAlgorithm({
  name: "my/outDegree",
  inputs: [{ kind: "relation", name: "edges" }],
  columns: ["node", "degree"],
  run: ([edges]) => {
    const counts = new Map<unknown, number>();
    for (const [from] of edges as unknown[][]) {
      counts.set(from, (counts.get(from) ?? 0) + 1);
    }
    return [...counts];
  },
});

const env = { ...stdlib, "my/outDegree": outDegree };
// ["query", ["my/outDegree", "edge", "?node", "?degree"]]

    The engine runs the algorithm once its input relations are complete, and its rows can feed rules, not, find, and aggregates. why marks them as computed.

    const env = { ...stdlib, URL };
await Effect.runPromise(run(
  ["object/get", ["object/new", "URL", "https://lionlang.dev/docs"], "pathname"], env));
// => "/docs"

    Evaluation rules

    How Lion evaluates each kind of JSON value: numbers, booleans, null, strings, arrays, and records.

    A Lion program is any JSON value. Evaluation depends only on the value's JSON type.

    JSON typeEvaluates to
    numberItself.
    booleanItself.
    nullItself.
    stringThe value bound to that name; otherwise a logic variable, for a name like "?x"; otherwise itself. See Strings.
    array[] for an empty array; otherwise a special form or a function call. See Arrays.
    object (record)A record with the same keys, each value evaluated. See Records.

    Strings

    A string is looked up in this order:

    1. If the environment binds the name, the string evaluates to the bound value.
    2. If the name has the form ?name, where name starts with a letter or _ and continues with letters, digits, _, or -, it evaluates to a logic variable. "?_" and names starting with ?_ are anonymous variables.
    3. If the name has the form module/name and reads as a misspelled name, it is an UnboundNameError that suggests the name: other names of its module are bound, as for "number/ad", or a bound name is a letter or two away, as for "numbr/add".
    4. Otherwise the string evaluates to itself, as "n/a" and "text/plain" do.
    ["begin",
  ["define", "name", "lion"],
  {"bound": "name", "unbound": "unbound text", "quoted": ["quote", "name"],
   "with a slash": "n/a"}]
    result 
    {
  "bound": "lion",
  "unbound": "unbound text",
  "quoted": "name",
  "with a slash": "n/a"
}
    ["number/ad", 1, 2]
    error 
    UnboundNameError: Nothing is bound to "number/ad". Did you mean "number/add"? To mean the string itself, write ["quote", "number/ad"].

    The misspelled name fails wherever it stands: as a function, as a value, as a schema, and inside a rule when the rule is written. ["quote", "number/ad"] is the string.

    To use a string that might be bound as plain text, wrap it in quote.

    Arrays

    • An empty array evaluates to [].
    • An array whose first element is the name of a special form or logic form, and whose shape fits that form, is evaluated by the form's own rules.
    • Any other array is a function call. Every element is evaluated, from left to right. The first must evaluate to a function, which is called with the rest as arguments. If it does not, evaluation fails with InvalidFunctionCallError.
    • An array that starts with a form's name but does not fit the form's shape, such as ["define", "x"], is treated as a call, and so fails with InvalidFunctionCallError.
    [1, 2, 3]
    error 
    InvalidFunctionCallError: [1,2,3] is not a valid call. The first element must be a special form or evaluate to a function.

    Records

    A record evaluates each value and keeps its keys as written, in order. A record with a logic variable among its values waits for it, as a call does. A record holds values, so a goal among them is asked: the record holds true or false. Keys are never evaluated. A key must not be empty or __proto__; a program with such a key fails with SchemaError before it runs.

    {"sum": ["number/add", 1, 2], "nested": {"ok": ["boolean/not", false]}}
    result 
    {"sum":3,"nested":{"ok":true}}

    Function calls

    • Arguments are evaluated before the call, from left to right.
    • A function may return a value or an Effect. Lion runs an Effect and uses its result.
    • A lambda called with fewer arguments than it has parameters fails with ArgumentMismatchError. Extra arguments are ignored.
    • A call with a logic variable among its arguments does not run. It waits: it becomes a value that a rule or query computes once the variable is bound. Every function waits this way, except relations, aggregates, graph algorithms, and lambdas, which take logic variables as they are.
    • A function that is given a goal with a relation in it gets the goal's answer, true or false: the goal is asked. Relations, aggregates, graph algorithms, and lambdas take the goal itself.
    ["number/add", "?n", 1]
    result 
    ["number/add","?n",1]

    Truthiness

    Where Lion tests a condition, as in cond, it uses JavaScript truthiness: false, null, 0, "", and NaN are false, and everything else, including [] and {}, is true. A condition that is a goal with a relation in it is asked first. match predicates are stricter: they must return the boolean true. So are and, or, not, and the filters of a rule or query, which take only true and false.

    Reserved names

    These names belong to forms and cannot be bound with define, used as lambda parameters, or declared as relations:

    begin, cond, define, eval, lambda, match, quote, relation, rule, fact, retract, query, find, why, not, and, or, =, in, snapshot, invariant, and __proto__.

    Each run

    Each evaluation (run in TypeScript, one file on the command line, one live example on this page) starts with a fresh environment holding the bindings it was given, and an empty logic database unless one is passed in. Names defined in one run are gone in the next; a shared database keeps its relations, facts, rules, and invariants. See Names, scope, and environments.

    Special forms

    The forms that control evaluation: quote, eval, begin, define, lambda, cond, and match.

    A special form is an array whose first element is the form's name. Unlike a function call, a special form decides which of its parts to evaluate, and when. The logic layer's forms are in Logic forms.

    quote

    ["quote", expression]

    Returns expression without evaluating it. Use it for literal lists, records that contain lists, and strings that might be bound names.

    ["quote", ["number/add", 1, 2]]
    result 
    ["number/add",1,2]

    eval

    ["eval", expression]

    Evaluates expression, then evaluates the result as a program in the current environment. The result must be JSON data; a function or other host value fails with SchemaError.

    ["eval", ["quote", ["number/add", 1, 2]]]
    result 
    3

    begin

    ["begin", expression, ...]

    Evaluates each expression in order and returns the last result. ["begin"] returns [].

    ["begin", ["define", "x", 1], ["define", "x", 2], "x"]
    result 
    2

    define

    ["define", name, expression]
    • Evaluates expression, binds name to the result in the global environment, and returns the result.
    • Always binds globally, even inside a lambda.
    • Binding a name again replaces its value. Functions that use the name see the new value when they next run.
    • name must be a non-empty string that is not a reserved name.
    ["begin",
  ["define", "greet", ["lambda", [], ["string/concat", "hello, ", "who"]]],
  ["define", "who", "world"],
  ["greet"]]
    result 
    "hello, world"

    lambda

    ["lambda", [parameter, ...], body]
    • Returns a function. Calling it binds each parameter to the matching argument, in a new environment whose parent is the one where the lambda was created, then evaluates body.
    • Called with fewer arguments than parameters, it fails with ArgumentMismatchError. Extra arguments are ignored.
    • The body is one expression; use begin for several.
    • Parameters must be non-empty strings that are not reserved names.
    ["begin",
  ["define", "makeAdder", ["lambda", ["n"], ["lambda", ["x"], ["number/add", "x", "n"]]]],
  ["define", "addTen", ["makeAdder", 10]],
  ["addTen", 5]]
    result 
    15

    cond

    ["cond", [condition, result], ..., ["else", result]]
    • Evaluates each condition in order and returns the evaluated result of the first one that is truthy. Later conditions are not evaluated.
    • A condition that is a goal with a relation in it, such as a relation call, is asked: it holds when the goal has a match.
    • An else branch, allowed only last, always matches.
    • With no match and no else, returns null.
    ["cond",
  [["number/greaterThan", 3, 5], "big"],
  [["number/greaterThan", 3, 1], "medium"],
  ["else", "small"]]
    result 
    "medium"

    match

    ["match", value, [schema, function], ..., fallback]
    • Evaluates value, then tries each pair in order. The first whose schema the value fits is chosen, and its function is called with the value. If the value fits none, fallback is called with the value.
    • Anything is a schema. A function is a predicate: the value fits when it returns true, and a failure, or any other result, counts as not fitting. A relation with one column is a predicate too: the value fits when the goal the relation builds from it has a match.
    • A record fits a record with the same keys, where each value fits the schema under the same key; ["schema/open", record] fits a record that has other keys too. A list fits a list of the same length, item by item. Any other value fits a value equal to it. Schemas nest.
    • At least one pair and the fallback are required.
    ["match", {"type": "user", "name": "Ada"},
  [{"type": ["func/partial", "string/equals?", "user"], "name": "value/string?"},
   ["lambda", ["u"], ["string/concat", "user ", ["object/get", "u", "name"]]]],
  ["lambda", ["other"], "unknown"]]
    result 
    "user Ada"

    A plain value, a list, and a schema built by the schema module are schemas too. The first pair here asks for a record with one key, so it does not fit; the third opens the record and takes it:

    ["match", ["quote", {"type": "refund", "amount": 5, "lines": [1, 2]}],
  [{"type": "refund"}, ["lambda", ["m"], "a refund and nothing else"]],
  [["schema/open", {"type": "sale"}], ["lambda", ["m"], "a sale"]],
  [["schema/open", {"type": ["schema/anyOf", "refund", "void"],
                    "lines": ["array/make", "value/number?", "value/number?"]}],
   ["lambda", ["m"], ["object/get", "m", "amount"]]],
  ["lambda", ["m"], "something else"]]
    result 
    5

    Logic forms

    The forms of Lion's Datalog-style logic layer: relations, facts, rules, queries, goals, questions, snapshots, and invariants.

    The logic layer stores facts in relations, derives more with rules, and answers queries. Relations, goals, and logic variables are ordinary Lion values, and answers are plain Lion data. For the rules every program must follow, see Logic database guarantees.

    Logic variables

    • An unbound string of the form "?name" evaluates to a logic variable. See Strings for the exact form.
    • The same name refers to the same variable throughout one goal or rule.
    • "?_", and any name starting with ?_, is anonymous: each occurrence is a separate variable, and it never appears in answers.
    • A call or record that mentions a logic variable waits for it.
    • A variable that only a question mentions belongs to the question.

    Goals

    A goal is a value that a query, rule, or invariant can solve. Goals are built by calling a relation, by not, and, or, =, and in, by calling a graph algorithm, and by calling any other function on logic variables, which makes a filter. The booleans true and false are goals that always and never hold. Any expression can also ask a goal.

    Waiting for values

    A rule or query is written before its variables have values. Anything that needs the value of a logic variable waits, and runs once for each answer that binds the variable.

    • A call waits when one of its arguments is a logic variable or a value that waits. Every function waits this way: standard functions, functions from the host, and functions made by func/partial.
    • cond waits when a condition is not known yet, match when its value is not, eval when its code is not, and a record when one of its values is not.
    • What a rule, query, or find holds runs when it does. A call on values that are already known may be computed when the rule is written, which changes nothing but when a side effect happens.
    • Relations, aggregates, and graph algorithms take logic variables as they are, and build goals and aggregates from them. A lambda's body runs right away, so a lambda can build goals; whatever in the body needs a value waits. Only an argument that asks a question makes a lambda's call wait, so the question is answered first, as it is in plain code.
    • What waits computes what it would compute with the value in place of the variable.
    • As a goal, a call that waits is a filter, and so is a variable. A filter must be true or false; any other value fails the query.
    • Names are replaced by their values when the rule or query is written, also inside a cond or lambda that waits. A lambda that calls itself by name still looks that name up each time it runs.
    ["begin",
  ["relation", "reading", ["sensor", "celsius"]],
  ["fact", ["reading", "attic", 30], ["reading", "cellar", 10]],
  ["query",
    ["and", ["reading", "?sensor", "?c"],
      ["=", "?summary",
        {"fahrenheit": ["number/add", ["number/multiply", "?c", 1.8], 32],
         "level": ["cond", [["number/greaterThan", "?c", 25], "hot"], ["else", "fine"]]}]],
    {"order": "sensor"}]]
    result 
    [
  {
    "sensor": "attic",
    "c": 30,
    "summary": {"fahrenheit":86,"level":"hot"}
  },
  {
    "sensor": "cellar",
    "c": 10,
    "summary": {"fahrenheit":50,"level":"fine"}
  }
]
    ["query",
  ["and", ["in", "?word", ["array/make", "apple", "cherry"]],
    ["string/indexOf", "?word", "a"]]]
    error 
    LogicError: A filter must be true or false, but ["string/indexOf","apple","a"] is 0.

    Asking questions

    A goal with a relation in it is a question, and any expression can ask it. As a goal of a rule or query it matches rows and binds variables. Anywhere else it is asked:

    • Under not, it holds when it has no match.
    • As a value, it is true when it has a match and false when it has none. A goal is a value in a cond condition, as an argument of a function, as an operand of = or in, as a value of a record or an argument of a fact, and as the value match looks at. A relation is a predicate for match and for functions that are given it, such as array/map.
    • find gives what it matches, as a list.
    • When a question is asked, the variables that the rule or query around it has bound have their values. Every other variable in it is the question's own: the question binds it, and it never appears in an answer. Two questions that use the same name for a variable of their own do not share it.
    • In plain code a question is asked right away, and every variable in it is its own. In a rule, query, invariant, or find, a question is part of what is written: it is asked for each answer, when that runs.
    • A question asked from a rule sees every row of the relations it asks about, so those are derived first. A rule cannot ask about a relation that depends on the rule's own head.
    • define, and, or, not, and a lambda keep a goal as it is, so goals can still be named, combined, and passed around.
    ["begin",
  ["relation", "parent", ["parent", "child"]],
  ["relation", "retired", ["name"]],
  ["fact", ["parent", "ada", "ben"], ["parent", "ada", "cy"], ["parent", "ben", "dee"]],
  ["fact", ["retired", "ada"]],
  {"children of ada": ["find", "?child", ["parent", "ada", "?child"]],
   "ada has a grandchild":
     ["cond", [["and", ["parent", "ada", "?c"], ["parent", "?c", "?_"]], "yes"], ["else", "no"]],
   "ben is retired": ["retired", "ben"],
   "who is retired": ["array/map", ["array/make", "ada", "ben"], "retired"]}]
    result 
    {
  "children of ada": ["ben","cy"],
  "ada has a grandchild": "yes",
  "ben is retired": false,
  "who is retired": [true,false]
}
    ["begin",
  ["relation", "parent", ["parent", "child"]],
  ["relation", "person", ["name"]],
  ["relation", "family", ["name", "children", "kind"]],
  ["fact", ["person", "ada"], ["person", "ben"], ["person", "cy"]],
  ["fact", ["parent", "ada", "ben"], ["parent", "ada", "cy"]],

    ["family", "?p",

    relation

    ["relation", name, [column, ...]]
["relation", name, [column, ...], {"key": column-or-columns, "schema": schema-name}]
    • Declares a relation in the current database and binds name to it in the global environment. Returns the relation, a function: calling it with one term per column builds a goal. Each term is a schema for its column: a value, a variable, a pattern, or a predicate.
    • Column names must be distinct. Options are read as written, not evaluated. They are "key" and "schema".
    • With a key, the relation holds at most one row per key: adding a fact whose key is present replaces the old row. A key can name one column or several.
    • With a schema, the name of a declared schema, every row must fit it, taken as a record of every column, so the schema names every column or is schema/open. The option adds the invariant ["invariant", ["and", [name, "?column", ...], ["not", [schema, {"column": "?column", ...}]]], {"assert": "none"}], and is nothing more: it must hold for the rows that are there, it is kept and reported like every invariant, and a snapshot writes it as one.
    • Declaring a relation that already exists with the same columns and key does nothing; declaring it with different ones fails. A relation cannot take the name of a schema.
    ["begin",
  ["relation", "order", ["id", "status"], {"key": "id"}],
  ["fact", ["order", 1, "open"], ["order", 1, "paid"]],
  ["query", ["order", "?id", "?status"]]]
    result 
    [{"id":1,"status":"paid"}]

    With a schema, a change that would leave a row that does not fit is refused. Here the schema is open, so it need not name the note column:

    ["begin",
  ["schema", "Order",
    ["schema/open", {"id": "value/integer?", "status": ["schema/anyOf", "open", "paid"]}]],
  ["relation", "order", ["id", "status", "note"], {"key": "id", "schema": "Order"}],
  ["fact", ["order", 1, "open", "gift"]],
  ["fact", ["order", 2, "lost", "none"]]]
    error 
    LogicError: Adding this fact breaks an invariant, so nothing changed. The invariant expected no answers but found 1, such as {"id":2,"status":"lost","note":"none"}: ["and",["order","?id","?status","?note"],["not",["Order",{"id":"?id","status":"?status","note":"?note"}]]]. {"id":2,"status":"lost","note":"none"} does not fit "Order": "status" must fit ["schema/anyOf","open","paid"] but is "lost".

    schema

    ["schema", name, shape]
["schema", name, shape, name, shape, ...]
    • Declares a schema in the current database and binds name to it in the global environment. Returns the schema, a function: calling it with a value says whether the value fits the shape.
    • shape is evaluated once, with the values its names have then, as a rule holds the values of its names. It can name the schema being declared, so a schema can describe nested data.
    • One form can declare several schemas, and each shape can name any of them, so schemas can be defined in terms of each other. A value fits only when that follows from the shapes in finitely many steps. A shape can name the schemas of its form but cannot call them, since they have no shape yet.
    • What a name in a shape means is settled when the shape is declared. A name that nothing has yet is a plain string, and nothing can be declared under it afterwards: the later form fails, and says to declare that name first, to declare the two in one form, or to write the string inside quote.
    • A schema that comes back to itself without going into the value does not fit: only 1 fits ["schema", "Loop", ["schema/anyOf", "Loop", 1]].
    • A shape cannot ask the database while it is declared, since a snapshot writes the shape and it must mean the same when loaded. A relation in a shape, or a lambda that asks, asks when a value is checked.
    • Declaring a schema that already exists with the same shape does nothing; declaring it with a different one fails. A schema cannot take the name of a relation.
    ["begin",
  ["schema", "Tree", {"value": "value/number?", "children": ["schema/arrayOf", "Tree"]}],
  {"fits": ["Tree", ["quote", {"value": 1, "children": [{"value": 2, "children": []}]}]],
   "problems": ["schema/problems",
     ["quote", {"value": 1, "children": [{"value": "two", "children": []}]}], "Tree"]}]
    result 
    {
  "fits": true,
  "problems": [
    {
      "path": ["children",0,"value"],
      "expected": "value/number?",
      "found": "two"
    }
  ]
}

    Schemas that one form declares can name each other. Here an expression is a number or a sum, and a sum holds expressions. Loop comes back to itself without going into the value, so only 1 fits it:

    ["begin",
  ["schema",
    "Expr", ["schema/anyOf", "value/number?", "Sum"],
    "Sum", {"add": ["schema/arrayOf", "Expr"]},
    "Loop", ["schema/anyOf", "Loop", 1]],
  {"a sum of sums": ["Expr", ["quote", {"add": [1, {"add": [2, 3]}]}]],
   "a word in it": ["Expr", ["quote", {"add": [1, {"add": [2, "x"]}]}]],
   "loop": ["array/map", ["array/make", 1, 2], "Loop"]}]
    result 
    {"a sum of sums":true,"a word in it":false,"loop":[true,false]}

    Declared in two forms, the first shape would take "Line" for a plain string, so the second form is refused:

    ["begin",
  ["schema", "Order", {"lines": ["schema/arrayOf", "Line"]}],
  ["schema", "Line", {"sku": "value/string?"}]]

    What fits a schema

    Anything is a schema, and one rule says what fits it. match, the functions of the schema module, a schema's own parts, and the schema of a relation's rows all ask through it.

    • A function is a predicate: a value fits when the function returns true. A failure, or any other result, counts as not fitting, except a misspelled name, which is an error. A relation with one column, a named schema, and a schema that a schema function built are functions. A relation with more columns is not the schema of one value, and using it as one is an error.
    • A record fits a record with the same keys, with values that fit. A key whose schema is schema/optional can be left out, and schema/open allows keys the record does not name.
    • A list fits a list of the same length, item by item.
    • Any other value fits a value equal to it.

    So data is a schema for itself: it fits exactly the values equal to it.

    {"a function": ["schema/fits?", 3, "value/number?"],
 "a record": ["schema/fits?",
   {"id": 1, "tag": "new"},
   {"id": "value/integer?", "tag": "value/string?"}],
 "a key too many": ["schema/fits?", {"id": 1, "tag": "new"}, {"id": "value/integer?"}],

   ["array/make", 2, "kg"],
   ["array/make", "value/number?", ["schema/anyOf", "kg", "lb"]]],

   ["array/make", 2, "kg", "net"],
   ["array/make", "value/number?", "value/string?"]],
 "a value": ["schema/fits?", "open", "open"],
 "data for itself": ["schema/fits?", ["quote", {"a": [1, 2]}], ["quote", {"a": [1, 2]}]]}
    result 
    {
  "a function": true,
  "a record": true,
  "a key too many": false,
  "a list": true,
  "a list too long": false,
  "a value": true,
  "data for itself": true
}

    A relation with one column is a predicate, so it is a schema: a value fits when it is one of the relation's rows.

    ["begin",
  ["relation", "person", ["name"]],

  "a person": true,
  "a stranger": [{"path":["owner"],"expected":"person","found":"cy"}]

A logic variable inside a schema is its value once it is bound, and until then it takes the value it meets; see Patterns. A schema that holds a relation asks the database when it checks a value, so a rule cannot use one that asks about the relation the rule derives.

    Patterns

    A schema with a logic variable in it is a pattern. Once the variable is bound it is its value, and until then any value fits it, and binds it. A pattern tests a value and takes it apart at once. These goals bind the variables of a pattern:

    • ["schema/fits?", value, schema] binds the variables in the schema.
    • A relation call binds the variables in its arguments, each a schema for its column. An argument that is not data, such as a predicate or a variable that holds one, is a schema like any other.
    • = and in bind the variables of a record or list, on either side of = or as the element of in. They compare values, so a function in the record is a value there, and not a predicate.
    • A record in a pattern fits a record with the same keys, and schema/open takes the keys it names from a record that has more. A list fits a list of the same length.
    • ?_ fits any value and binds nothing. A variable that occurs twice must take the same value.
    • Every schema function works in a pattern. schema/anyOf gives the answers of every schema that fits, each once; in plain code, where nothing is left to bind, the first that fits decides.
    • A predicate made from a variable, as ["func/partial", "number/lessThan", "?max"] is, is the predicate made from the variable's value.
    • ["schema/open", "?shape"] does not bind ?shape: it waits for another goal to bind it to a record of schemas.
    • A goal gives the same answers whether it binds a variable through a pattern or finds it bound by another goal, so the order of a body's goals does not matter.
    • In plain code, a check with an unbound variable in it is a goal, like = with one. Give it to query.
    ["begin",
  ["relation", "inbox", ["doc"]],
  ["fact",
    ["inbox", ["quote", {"type": "order", "id": 1, "lines": [{"sku": "a1", "qty": 2}]}]],
    ["inbox", ["quote", {"type": "order", "id": 2, "lines": [], "rush": true}]],
    ["inbox", ["quote", {"type": "refund", "id": 3}]]],
  {"refunds": ["query", ["inbox", {"type": "refund", "id": "?id"}]],
   "orders": ["find", "?id", ["inbox", ["schema/open", {"type": "order", "id": "?id"}]]],
   "lines": ["find", ["array/make", "?order", "?sku"],
     ["and",
       ["inbox", ["schema/open", {"id": "?order", "lines": "?lines"}]],

    fact

    ["fact", goal, ...]
    • Adds each fact, a relation call with JSON data and no logic variables, and returns the facts given. A question among a fact's arguments is asked, and the fact holds its answer.
    • A relation's facts are a set; adding a fact that is present changes nothing.
    • For a keyed relation, a fact replaces the row with the same key; within one form, the last fact for a key wins.
    • A relation that rules aggregate into, or that a graph algorithm computes, cannot have facts.
    • The form is one change: it is checked in full, made in full, and checked against every invariant, or it fails and changes nothing.

    retract

    ["retract", goal, ...]
    • Removes each fact, and returns the facts that were present and removed.
    • A row of a keyed relation is removed only when every column matches.
    • Facts derived by rules cannot be retracted; derived answers update on the next query.
    • Like fact, the form is one all-or-nothing change.
    ["begin",
  ["relation", "edge", ["from", "to"]],
  ["fact", ["edge", "a", "b"], ["edge", "b", "c"]],
  ["retract", ["edge", "a", "b"], ["edge", "x", "y"]]]
    result 
    [["edge","a","b"]]

    rule

    ["rule", head, goal, ...]
    • Adds a rule: head, a relation call, holds for every way of satisfying all the goals. Returns the rule as written, with values as evaluated.
    • Head arguments can be values, variables bound by the body, computed values, questions, and aggregates.
    • The rule is checked when added: every head variable must be bound by the body, every goal must be safe, and the whole program must stay stratified and terminating. A rule that fails a check is not added.
    • An or in the body makes one rule with several alternatives.
    • Adding a rule the database already holds, one a snapshot would write the same way, changes nothing.
    • Adding a rule is one all-or-nothing change, checked against every invariant.

    query

    ["query", goal]
["query", goal, options]
    • Returns one record per distinct answer, with one key per named variable, without its ?. A goal with no variables returns [{}] when it holds and [] when it does not. A variable that only a question in the goal mentions is not part of an answer.
    • Without the "order" option, answers come in the order they are found, which can change between versions of Lion.
    • Options sort, page, and assert on the answers; see Query options.
    ["begin",
  ["relation", "edge", ["from", "to"]],
  ["fact", ["edge", "a", "b"], ["edge", "a", "c"]],
  {"targets": ["query", ["edge", "a", "?to"], {"order": "to"}],
   "holds": ["query", ["edge", "a", "b"]],
   "fails": ["query", ["edge", "b", "a"]]}]
    result 
    {"targets":[{"to":"b"},{"to":"c"}],"holds":[{}],"fails":[]}

    find

    ["find", template, goal]
    • Returns the value of template for every match of goal, as a list. The template is any expression over the goal's variables: a variable, a record, a call, or another find.
    • The list is sorted, in the order that values sort in, so it never depends on how the matches were found. A template such as ["array/make", "?points", "?name"] sorts by points first.
    • Every match gives one value, so the list can repeat a value, as aggregate/collect does. A match that several alternatives of an or find gives one. Use aggregate/unique for distinct values.
    • The goal must bind every variable of the template that the rule or query around the find does not.
    • A find is a question: in plain code it is asked right away, and in a rule, query, or another find it is asked for each answer, with the variables that answer has bound.
    • An aggregate of a find combines what it found, also as a whole argument of a rule head. A find with no match is an empty list, so a count of it is 0.

  ["relation", "customer", ["name"]],
  ["relation", "order", ["id", "customer", "amount"]],
  ["fact", ["customer", "ana"], ["customer", "bo"], ["customer", "cy"]],

    ["customer", "?c"]]]

    why

    ["why", fact]
    • Returns a tree that explains how fact, a relation call with no variables, holds, or null when it does not.
    • Each node has a fact, and either "given": true, "computed": true for a graph algorithm's row, or the rule that derived it with the premises it used under because.
    • Premises are facts, {"check": goal} for a filter that held, and {"absent": goal} for a goal under not, each written with the answer's values in place of its variables. A variable that a question binds for itself keeps its name.
    • An aggregated fact lists every match it combines under matches; for min, max, and shortest, it explains the match that produced the value.
    • A relation goal's premise is the row it matched, also when the goal says which rows with a pattern or a predicate. A schema check that held is a check.
    • Explanations use every relation computed in full.

    and

    ["and", goal, ...]

    Holds when every goal holds, sharing variables between them. On booleans it is the boolean operator: it reads its arguments in order and stops at the first that is false, so later arguments are not evaluated.

    or

    ["or", goal, ...]

    Holds when any goal holds. On booleans it is the boolean operator, and stops at the first argument that is true. An answer leaves out a variable that the alternative it came from does not bind. A choice between filters is one test; goals that combine and and or over relations may expand to at most 64 alternatives.

    =

    ["=", term, term]

    Binds an unbound variable on either side to the other side's value, or tests that both sides are equal. A side can be a record or list with variables in it, a pattern that takes the other side apart. Without logic variables, it is structural equality of JSON values, and identity for other values. The numbers 0 and -0 are equal, as JSON writes both as 0.

    in

    ["in", element, list]

    snapshot

    ["snapshot"]
    • Returns a begin program that rebuilds the current database: a relation form per relation, a schema form for the schemas each schema form declared, a fact form per relation with facts, every rule, and every invariant, in that order.

    invariant

    ["invariant", goal, {"assert": "none"}]
["invariant", goal, {"assert": "some"}]
    • Adds a query assertion the database keeps: the goal must have no answers ("none") or at least one ("some"). Returns the invariant as written.
    • The goal is compiled and checked like a query's. The options record is read as written and must hold exactly "assert".
    • The invariant must hold when added; otherwise it is not added.
    • After that, every fact, retract, and rule form is checked against every invariant once it has made all of its changes. A form that breaks one, or whose check fails, is undone and fails, leaving the database exactly as it was.
    • Adding an invariant the database already holds changes nothing. Invariants cannot be removed.
    ["begin",
  ["relation", "edge", ["from", "to"]],
  ["invariant", ["edge", "?x", "?x"], {"assert": "none"}],
  ["fact", ["edge", "a", "b"], ["edge", "c", "c"]]]
    error 
    LogicError: Adding these facts breaks an invariant, so nothing changed. The invariant expected no answers but found 1, such as {"x":"c"}: ["edge","?x","?x"].

    Query options

    The options record of a query: order, offset, limit, and assert, and the order Lion sorts values in.

    A record after a query's goal sorts, pages, and asserts on its answers. Options are read as written, not evaluated. An unknown option, or an option with a value of the wrong kind, fails with a message that names it.

    ["query", goal, {"order": ["-points", "player"], "offset": 10, "limit": 5, "assert": "some"}]
    OptionValueMeaning
    "order"A variable name, or a list of themSorts answers by each variable in turn. A leading - sorts that variable from largest to smallest. The ? is optional. Each must be a variable of the query.
    "offset"A whole number of at least 0Skips that many answers, after sorting.
    "limit"A whole number of at least 0Returns at most that many answers, after the offset.
    "assert""some" or "none"Fails the query when it has no answers ("some") or any ("none"). It sees every answer, before offset and limit.

    Value order

    Sorting compares values of different types in a fixed order: null, then booleans (false before true), numbers, strings, lists, and records. Lists compare item by item, and records by their entries sorted by key. Strings compare by UTF-16 code units, so uppercase letters sort before lowercase ones.

    ["begin",
  ["relation", "item", ["value"]],
  ["fact", ["item", "b"], ["item", 2], ["item", null], ["item", true],
    ["item", "B"], ["item", ["array/make", 1]], ["item", {"k": 1}]],
  ["query", ["item", "?value"], {"order": "value"}]]
    result 
    [
  {"value":null},
  {"value":true},
  {"value":2},
  {"value":"B"},
  {"value":"b"},
  {"value":[1]},
  {"value":{"k":1}}
]

    Assertion messages

    A failed assertion reports the goal and, for "none", how many answers it found and the first one:

    ["begin",
  ["relation", "edge", ["from", "to"]],
  ["fact", ["edge", "a", "b"]],
  ["query", ["edge", "?from", "?to"], {"assert": "none"}]]
    error 
    LogicError: The query expected no answers but found 1, such as {"from":"a","to":"b"}: ["edge","?from","?to"].

    An invariant uses the same assertions and the same wording.

    Standard library

    Every function in Lion's default environment, by module: number, boolean, string, array, value, schema, object, func, console, aggregate, and graph.

    The default environment, stdlib, names each function module/function. Functions check their arguments and fail with SchemaError when one has the wrong type. Each module's example below calls every function in the module.

    Every function waits when it is called with a logic variable among its arguments, so all of them work as filters and computed values in rules and queries. A function that is given a goal gets its answer, true or false; see Asking questions. Functions of the aggregate and graph modules take logic variables as they are, to build aggregates and goals.

    Logic database guarantees

    The rules every logic program follows, what Lion checks and when, and what it promises about changes and answers.

    The logic database checks rules, goals, and changes as they arrive, so that every program has one well-defined answer, evaluation always finishes, and the data never ends up half changed.

    Safety

    • Every variable in a rule's head must be bound by a goal in its body.
    • Every variable in a filter, in a computed value, or in an input of a graph algorithm must first be bound by a relation goal, =, in, or schema/fits?. An input of a graph algorithm must be data.
    • A question, a goal under not, a goal used as a value, or a find, waits for the variables that the rule or query around it binds. Every other variable in it is its own, and the question must bind it itself. A find must bind every variable of its template.
    • The list in in must be bound before it runs.
    • Lion orders the goals of a body so each runs once its inputs are bound. Filters that are ready together run in the order written, so a guard written first protects the filter after it. Otherwise the order you write goals in only matters for goal-directed queries.

    A rule, query, or invariant that breaks a safety rule fails when it is added or run, with a message that names the unbound variable.

    Values

    • A value computed from a logic variable is what the same expression gives with the variable's value in its place. This holds for every function, for cond, match, eval, and records, for lambdas, and for the questions an expression asks: a goal used as a value and a find give in a rule what they give in plain code.
    • A filter must be true or false. The rows a rule derives and the answers a query gives must be JSON data. Anything else fails with an error that shows the call or the value.
    • A function that fails while a rule or query runs it fails the rule or query, with an error that names the call and the values it ran on.
    • Whether a value fits a schema is the same wherever it is asked: in plain code, under the schema's name, in a rule or query, in match, as an argument of a relation call, and as the schema of a relation's rows.
    • A goal that binds variables through a pattern gives what the same goal gives when another goal has bound those variables first, so the answers of a body do not depend on the order of its goals.

    Questions and aggregation

    • A rule cannot ask a question about a relation that depends on the rule's own head, directly or through other rules. That covers a goal under not, a goal used as a value, a find, and a relation handed to a function. A question that a rule only builds when it runs, as with eval, fails then instead.
    • An aggregate runs once its inputs are complete. Aggregation may go through recursion only with the lattice aggregates aggregate/min, aggregate/max, aggregate/shortest, and aggregate/union, and only when every relation in the recursive cycle aggregates.
    • Every rule for an aggregated relation must aggregate the same columns in the same way, and an aggregated relation cannot have facts.

    Together these make every program stratified: it has a single answer, whatever order rules were added in.

    Termination

    • A recursive rule cannot compute a new value for its head, in the head itself or through = or in. Values that come from facts are fine. So recursion only combines values that already exist, and stops.
    • Recursion through a lattice aggregate stops when no value improves. If values still improve after 10,000 rounds, as with a negative-weight cycle under aggregate/min, the query fails instead of running forever.
    • A graph algorithm cannot be part of a recursive cycle.

    Keys

    • A keyed relation holds at most one row per key. A fact with a key that is present replaces the old row.
    • Rules can derive rows of a keyed relation, but two different derived rows with the same key make the query fail, naming both rows.

    Changes are all or nothing

    A form that changes the database, fact, retract, or rule, either makes all of its changes or fails and makes none of them. Every fact is checked before any is added or removed, and every rule before it is added. When the database has invariants, the form is checked against them after making its changes, and undone if any breaks or cannot be checked, leaving the database exactly as it was, facts in the same order. Separate forms are separate changes.

    A change to facts is checked against the invariants that read what it changed, and an invariant that expects no answers is asked about the new rows alone when its goal matches the rows of the relation that changed. That is only a faster way to the same verdict: a change is kept exactly when every invariant still holds.

    Adding what is already held

    Adding something the database already holds changes nothing: a fact that is present, a relation or schema declared the same way, or a rule or invariant that a snapshot would write the same way. Rules and invariants hold values as they were evaluated, so a name and the value bound to it are the same, whether the value is data or a function, while a variable "?x" and the string ["quote", "?x"] differ. Running a program twice against one database therefore leaves it as running it once did.

    Equivalent ways to answer

    • Goal-directed and full evaluation give the same answers, possibly in a different order. A goal-directed query derives only the rows it asks about, so it does not fail on a row it never derives.
    • What the database has derived for earlier queries never changes an answer: a query gives what it would give on a database that has derived nothing yet.
    • A snapshot, evaluated into an empty database, gives the same answers as the database it was taken from, and taking a snapshot of that gives the same program.
    • The relation option "schema" and the invariant it stands for keep the same changes, with the same messages, and are saved as the same snapshot.
    • Answers are cached until a fact, rule, or invariant changes; a cached answer is the answer evaluation would give.

    Answer order

    Without the "order" option, a query's answers come in the order they are found. That order is deterministic for a given program and version of Lion, but it is not part of the language. Sort with "order" when order matters. A find always returns its list sorted, so a value a rule derives from one never depends on how it was found.

    Errors

    Every way a Lion program can fail, the error's tag, and what causes it.

    A failed evaluation is a typed Effect failure. Each error has a _tag you can catch with Effect.catchTag. On this page and in the editor, failures show as Tag: message.

    TagRaised when
    SchemaErrorThe program is not a valid Lion expression, such as a record key __proto__; a function receives an argument of the wrong type; or eval is given something that is not JSON.
    UnboundNameErrorA string of the form module/name is evaluated, nothing is bound to it, and it reads as a misspelled name: other names of its module are bound, or a bound name is a letter or two away, which the message suggests. The error holds the string as unbound and the suggestion, or null, as nearest. Inside quote the string is data.
    InvalidFunctionCallErrorAn array's first element does not evaluate to a function, including a name that nothing is bound to and a form's name used with the wrong shape. A misspelled module/name is an UnboundNameError instead.
    ArgumentMismatchErrorA lambda is called with fewer arguments than it has parameters.
    ArithmeticErrorArithmetic has no finite result, such as division by zero or an overflow. JSON cannot hold Infinity or NaN.

    Why programs are JSON

    What Lion gains by making every program a JSON value, what it costs, and how the evaluation rules make it work.

    Most languages have a syntax of their own, and a parser that turns text into a tree the evaluator walks. Lion skips the syntax. A Lion program is already the tree, written as JSON, and the evaluator walks it directly. This page explains why that is worth doing, and what it costs.

    Code that other systems can handle

    JSON is the one data format almost every system already speaks. Databases store it, HTTP carries it, queues pass it along, and every language can read and write it without a new library. When programs are JSON, all of that infrastructure works on programs too. A rule can live in a database row and be edited by an admin screen. A workflow can arrive in a request body. A diff of a program is a diff of JSON.

    It also matters for programs that write programs. A language model, a form builder, or another service can produce a Lion program by producing JSON, and a JSON schema can describe what it may produce. There is no grammar to get wrong and no string escaping to forget.

    Code is data, so data can become code

    Lisp's old idea is that code and data share one shape, so a program can build and inspect programs with the same tools it uses on any list. Lion inherits this, which is why it is called a Lisp. A program is a list; quote holds one without running it, list functions take it apart and put it together, and eval runs the result. The how-to guide on code as data shows this in practice, and the graph editor relies on it: it edits the JSON tree and nothing else.

    How JSON becomes code

    Every JSON value has to mean something when evaluated, and Lion's rules are chosen so that the common case needs no ceremony:

    • Numbers, booleans, and null mean themselves, so plain data is a valid program.
    • Records evaluate their values and keep their keys, so a record is both a data structure and a way to return several results at once.
    • Arrays are calls, because calls are the heart of a Lisp, and an array is the only JSON shape with an obvious first element.
    • Strings are the one compromise. JSON has no separate type for names, so a string is a name when something is bound to it and text otherwise.

    The full rules are in Evaluation rules.

    What it costs

    The string compromise is the main cost. A string in your data that happens to match a bound name, such as "number/add", evaluates to that function, and a list in your data is a call. quote is the way out, and the reason snapshots quote such strings when they save a database. Namespacing every library name with a / makes accidental matches rare.

    JSON is also more verbose than a syntax designed for people, and it has no comments. Lion leans on tools for this: the graph editor shows the tree with each form labeled, and records can carry descriptions alongside code. For programs that machines write and people review, the trade is usually worth it.

    Why not just use JavaScript?

    A host language like JavaScript can do everything Lion can, but its programs are text that must be parsed, and running untrusted JavaScript means trusting it with everything the host can reach. A Lion program can only call what its environment binds. The host decides exactly which functions a program may use, so a program from a database, a user, or a model is as safe as the environment it runs in.

    Names, scope, and environments

    How Lion looks up names, why define is global while lambdas are lexical, and what lasts from one run to the next.

    Every string in a Lion program might be a name. This page explains where names come from, how a lookup finds them, and how long they last.

    Environments are chains

    An environment is a record of bindings with an optional parent. Looking up a name checks the current environment, then its parent, and so on to the top. A run starts with one top-level environment holding whatever the host gave it, usually the standard library.

    Calling a lambda makes a new environment for its parameters whose parent is the environment where the lambda was created, not where it is called. That is lexical scope: a lambda remembers the names around it.

    ["begin",
  ["define", "counterFrom", ["lambda", ["start"],
    ["lambda", ["step"], ["number/add", "start", "step"]]]],
  ["define", "fromTen", ["counterFrom", 10]],
  ["define", "start", 1000],
  ["fromTen", 5]]
    result 
    15

    The global start is 1000, but the inner lambda sees the start it was created with, 10.

    Why define is global

    define always writes to the top-level environment, even inside a lambda. Lion has no local variables beyond parameters; to name an intermediate value inside a function, pass it to another lambda, or compute it in a begin at the top level.

    This keeps the model small: there is exactly one place where definitions go, and a program reads top to bottom like a script. It also means lambdas see later definitions, because they look names up when they run:

    ["begin",
  ["define", "greet", ["lambda", [], ["string/concat", "hello, ", "name"]]],
  ["define", "name", "Ada"],
  ["greet"]]
    result 
    "hello, Ada"

    So top-level functions can refer to each other in any order, which mutual recursion needs.

    Parameters shadow globals

    A parameter with the same name as a global hides the global inside the lambda's body. Because standard library names contain a /, choosing parameter names without one keeps them from shadowing a library function by accident.

    Strings that name nothing

    A string that nothing is bound to is itself, which is what lets a program write "open" for a status without any quoting. The cost is that a misspelled name would quietly become a string: ["number/ad", 1, 2] would be a call to a string, and "value/intger?" as a schema would be a string that only the same string fits.

    So Lion looks at one more thing. A string of the form module/name that reads as a misspelled name is an error. It reads that way when other names of its module are bound, or when a bound name is a letter or two away, which the error then suggests. Any other string with a slash in it, such as "n/a" or "text/plain", is data as before.

    ["array/map", ["array/make", 1, "two"], "value/numbr?"]
    error 
    UnboundNameError: Nothing is bound to "value/numbr?". Did you mean "value/number?"? To mean the string itself, write ["quote", "value/numbr?"].

    A host that adds functions under its own module gets the same check for them: once "shop/stock" is bound, "shop/stok" is an error. Inside quote, a string is always data.

    What lasts between runs

    Names last for one run. Each run, whether a call to run, one file on the command line, or one example on this page, starts with a fresh environment, so nothing a program defines leaks into the next.

    The logic database is different. It is not part of the environment; it is a separate store that a host can pass to several runs, and that the command line keeps in a file. Relations and schemas declared in a shared database are bound by name in every run that uses it, unless the host binds the same name. This split is deliberate: definitions are code, and code is re-run, while facts are state, and state persists.

    Functions are Effects

    A Lion function returns an Effect, a description of work, rather than a plain value. Evaluation is itself an Effect, so a function can do anything an Effect can, such as wait for a network call or fail with a typed error, and the evaluator composes it with everything else. Host functions may return plain values or Effects; Lion handles both. This is why func/callback exists: it turns a Lion function into an ordinary JavaScript function for APIs that expect one.

    How Lion answers logic questions

    Why Lion's logic layer is Datalog rather than Prolog, how it computes answers bottom-up, and where its restrictions come from.

    Lion's logic layer lets a program state facts and rules and ask questions, instead of spelling out how to find answers. This page explains the model behind it, and why its rules are what they are.

    Goals are values

    In most logic languages, rules and queries are a separate syntax. In Lion, calling a relation, such as ["parent", "?p", "eli"], just returns a goal value. Goals can be stored, passed to functions, and combined with and, or, and not, like any other value. A query, rule, or invariant solves them, and so does any expression that needs their answer. This keeps the logic layer inside the language: a lambda can build goals, answers come back as ordinary data, and a relation can be tested like any other condition.

    Datalog, not Prolog

    Prolog answers a question by searching backward from it, trying rules in order. That is powerful, but a query can run forever, and the answer can depend on the order rules were written in.

    Lion follows Datalog instead. Datalog computes forward: it starts from the facts, applies every rule to derive new facts, and repeats until nothing new appears. Because the facts and the values in them are finite, and rules only combine values that already exist, this always stops, and the result does not depend on rule order. The price is expressiveness. A recursive rule cannot invent new values without limit, which is why Lion rejects a recursive rule that computes a value in its head.

    Semi-naive evaluation

    Re-applying every rule to every fact in each round would redo the same work again and again. Lion's evaluation is semi-naive: each round only considers matches that use at least one fact that is new since the last round, and starts each join from those new facts. A query along a 3,000-step chain takes milliseconds rather than seconds this way.

    Stratification

    A question needs a complete picture. "Customers with no orders" is only right once every order is known, and so is a total, a list of what a goal matches, or the plain fact that it matches anything. Lion therefore groups relations into strata, ordered by what depends on what, and derives a relation fully before any rule that asks about it or aggregates it. It does so the first time something reads the relation, and keeps the rows until a fact or rule changes. A rule that asks about a relation that depends on its own head has no correct stratum, so such a rule is rejected when added.

    Lattice aggregates are the exception. min, max, shortest, and union only move one way as values arrive: a minimum only gets smaller. A partial result is never wrong, only not yet final, so these may aggregate through recursion. That is how a rule can compute shortest distances, and why a negative-weight cycle, where a distance would shrink forever, is stopped after 10,000 rounds.

    Whatever needs a value waits

    A rule body mixes relation goals with filters such as ["number/greaterThan", "?amount", 50]. When Lion evaluates that call, ?amount has no value yet. So the call does not run: it becomes a value that stands for the call, and the engine runs it once for each answer that binds ?amount. The engine plans the body so each filter runs as soon as its variables are bound, which is why goals may be written in any order, and why a filter whose variables are never bound is an error rather than a silent miss.

    The same one rule covers everything else that needs a value. Any function waits, whether it comes from the standard library or the host. A cond waits when its condition is not known, a match when its value is not, and a record when one of its values is not. Each of them is written back out, in a snapshot or an explanation, as the form it was. And each computes exactly what it would compute with the value in place of the variable, so there is nothing new to learn about how an expression behaves inside a rule.

    Only the things that build logic do not wait: relations, aggregates, and graph algorithms take a variable as it is and make a goal of it. A lambda's body runs right away for the same reason, so a lambda can build goals, while whatever inside it needs a value waits.

    Whatever needs an answer asks

    The waiting rule lets ordinary expressions live inside rules. Its mirror image lets rules live inside ordinary expressions. A goal with a relation in it is a question, and whatever needs its value asks it: a cond condition, a function argument, not, or find, which returns what the goal matches as a list. In plain code the question is asked right away. Inside a rule it waits like everything else, and is asked once for each answer, with that answer's values in place.

    The two rules meet without a seam. A question sees the variables its surroundings have bound, and owns the rest, so the same find means the same thing at the top of a program and deep inside a rule. That is also what makes it safe to move code into a lambda: a lambda that asks gives the same answers wherever it is called.

    Explanations come free

    Because evaluation derives each fact from specific earlier facts, it can remember which rule produced it, and for which answer of the rule's body. why reads that record back as a tree of the facts and tests the answer rested on.

    When rules are not enough

    Some questions are awkward or slow as rules, such as PageRank or Dijkstra's shortest paths. Rather than force them into rules, Lion lets algorithms be goals. A graph algorithm runs once its input relation is complete and contributes rows like a relation, so its answers can feed rules, negation, and aggregates. See Answer graph questions.

    Goal-directed evaluation

    How Lion avoids deriving everything a program implies when a query only needs a little, and why the shape of a recursive rule matters.

    Bottom-up evaluation derives every fact a program implies. Usually a query needs far less: asking for the paths from one node does not need the paths from every other node. This page explains how Lion narrows the work, and what that means for how you write rules.

    Passing the question down

    When a query gives a rule-defined relation a known argument, as "a" in ["path", "a", "?to"], Lion rewrites the rules before evaluating them, using a technique called magic sets. Each relation gets a copy specialized to which of its arguments are known, and extra rules pass those known values down through the rule bodies. Evaluation then only derives facts the query can reach. A query along a 3,000-node chain that would derive about 4.5 million paths in full returns its three answers in milliseconds.

    An argument is known when it is a value, a variable the query has already bound with a relation, =, or in, or a value computed from such variables, as in ["path", ["number/add", "?s", 1], "?to"]. Inside a rule, only values and variables bound from facts count, so the rewritten rules never ask about values without end.

    The rewrite changes how much is computed, never what the answers are. Lion still evaluates bottom-up; it just starts from the question's own values.

    Why the shape of a rule matters

    The rewrite passes known values from left to right through a rule's body. Compare two ways of writing paths from a known start:

    • Recursion first: ["path", "?x", "?z"], ["path", "?x", "?y"], ["edge", "?y", "?z"]. The known start ?x passes straight into the recursive call, so every step asks about the same start.
    • Edge first: ["path", "?x", "?z"], ["edge", "?x", "?y"], ["path", "?y", "?z"]. The recursive call asks about ?y, each node along the way, so the question spreads to every reachable node, which can cost as much as computing everything.

    Both give the same answers. With a known start, write the recursion first; with a known end, put it last. Follow relationships of any length shows both.

    What is still computed in full

    Some relations cannot be narrowed safely. A relation that is aggregated, computed by a graph algorithm, or asked about, under not, in a find, or as a value, needs its complete contents to be right, so Lion derives it, and everything it depends on, in full. Explanations from why also use full evaluation, so they describe the program as written.

    Even then Lion does no more than it must. A relation is derived the first time something reads it, and kept until a fact or rule changes, so a query never pays for relations it does not touch, and later queries reuse what earlier ones derived.

    Turning it off

    A host can create a database with new LogicDatabase({ goalDirected: false }) to derive every row of the relations a query reads. This is useful for comparing results; Lion's own tests check that both ways agree.

    One set of rules for every feature

    Why Lion's features share the same few rules, how that follows from the principle of least astonishment, and how Lion settles the places where JavaScript and JSON disagree.

    Lion is small, and its value comes from features that combine: a query option inside an invariant, a graph algorithm under not, a snapshot run by the command line. Features only combine well if they agree on the basics. This page explains the rules they share, and the principle behind them.

    The principle of least astonishment

    A feature should do what someone who already knows Lion expects, both on its own and next to every other feature. In practice that means reusing what exists before inventing more, and when a feature needs a rule, following the rule a similar feature already has. A user who learns one rule then knows how every feature behaves.

    Reuse before invention

    Invariants are the clearest example. Lion already had a way to say "this question must have no answers": the query option "assert": "none". An invariant is that same assertion, kept by the database. It takes the same option, compiles its goal like a query, is answered by the same engine, and fails with the same words. There is no second vocabulary to learn, and anything a query can ask, an invariant can require.

    Changes are all or nothing

    Every form that changes the database, fact, retract, or rule, either completes or changes nothing. This one rule answers many questions at once. What happens to the facts before a bad one in a retract? Nothing, because the form fails as a whole. What does a broken invariant leave behind? Nothing, because the change is undone, down to the order facts come back in. What if checking an invariant itself fails? The same: the change is undone.

    The unit of change is one form, not one run. That keeps the rule simple and lets several facts that only make sense together go in a single fact form, while each later form is checked against the result.

    Adding what is held changes nothing

    Facts are a set, so adding a fact twice changes nothing; declaring a relation twice the same way changes nothing. Rules and invariants follow the same rule: adding one the database already holds, one a snapshot would write the same way, changes nothing. Before this was true for rules, running a setup program twice against a saved database added each rule again, and aggregates silently counted every match twice. One rule for every kind of definition removed that whole class of surprise.

    One rule for everything that waits

    Inside a rule or query, a logic variable has no value yet. Lion has one answer to that everywhere: whatever needs the value waits until the variable is bound, and then computes what it would compute with the value in its place. That holds for a standard function and a host function, for cond, match, and eval, for a record, and for a lambda passed to array/map. No function has to be marked for it, and no form behaves differently inside a rule than outside.

    The forms that test truth follow one rule too. and, or, and not accept only true, false, and goals, and so does a filter: a filter that gives a number is an error, not a guess at what the number means. and and or stop at the first argument that decides them, as booleans and as goals.

    One rule for every question

    A goal is a question, and Lion has one answer to "who may ask it": anything. A rule or query asks a goal for its matches. not asks whether it has none. A cond condition, a function argument, or a value of a record asks whether it has any. find asks for all of them, as a list. There is no separate way to "call the database" from an expression, and no place where a relation call is refused.

    Wherever a question is asked, the same thing happens to its variables: the ones the surroundings have bound keep their values, and the rest belong to the question. In plain code nothing is bound, so the question is asked as it stands. In a rule, it is asked once for each answer of the rule. That one rule replaced three special ones. not no longer has its own restriction on variables. A relation works as a predicate without being marked as one. And an aggregate needs no second meaning to be used in a query or to count zero: it combines the list that find gives it.

    One limit follows from asking, and it is the limit negation always had: a rule cannot ask about a relation that depends on the rule's own head, because the answer would not be settled when the rule needs it.

    One rule for what fits

    Checking data is usually a second language beside the first: a schema library at the edge of a program, with its own types, its own combinators, and its own errors. Lion has no second language. A schema is anything a value can fit, and one rule says what fits: a function is a predicate, a record or list fits part by part, and any other value fits a value equal to it. match already chose its branches this way, so its patterns and schemas are the same thing. Data is then a schema for itself, since a value with no function in it fits exactly the values equal to it.

    The other rules then do the rest. A schema check is a call, so it waits for logic variables, and a rule can use it as a goal with nothing added. A logic variable in a schema is the value it meets, so the schema that checks a record is the pattern that takes it apart, and a relation call is a schema for a row: each argument says what its column must be. A relation is a predicate, so a relation is a schema, and as the schema of a column it is a foreign key. The schema of a relation's rows is an invariant, written in the vocabulary invariants already have, so it is all or nothing, reported in the same words, and saved by a snapshot like any other.

    Equivalent programs behave the same

    A snapshot is a program that rebuilds the database, so loading one must give the same answers, and saving again must give the same program. Goal-directed and full evaluation must give the same answers. A name and the value bound to it are the same inside a rule, because rules hold values as evaluated; that goes for a function as much as for a number. An expression over a logic variable must give what it gives with the value in the variable's place, and that includes every question the expression asks. What a database has already derived must never change an answer. A schema fits the same values under its name, and a relation's schema keeps exactly what the invariant it stands for keeps. Each of these is tested as a property over generated programs, so a change that breaks one fails the test suite.

    Where JavaScript and JSON disagree

    Lion runs on JavaScript, but its values are JSON, and the two disagree in a few places. Each time, Lion follows JSON, and applies the choice everywhere it comes up:

    • Numbers are finite. JavaScript has Infinity and NaN; JSON does not. So arithmetic whose result is not a finite number, such as dividing by zero, fails with ArithmeticError rather than producing a value that cannot be printed, stored as a fact, or saved in a snapshot. Facts and rule results already refused such numbers; the number functions and list aggregates now refuse them at the source.
    • Nothing is null. JavaScript has both undefined and null; JSON only has null. So every "there is nothing here" answer is null: a missing key from object/get, the first item of an empty list, the mean of no values, a cond with no match.
    • Records and lists are different kinds. To JavaScript's typeof, a list is an object; to JSON, it is not. So value/object? is true for records and not for lists, and value/array? is the test for lists.
    • Keys belong to objects; methods belong to any value. Reading a key needs an object, so object/get and paths pass only through objects. But a string has methods, as JavaScript's "lion".toUpperCase() shows, so every method function works on any value except null.

    One difference remains by design: without the "order" query option, the order of a query's answers is deterministic for a given program and version of Lion, but not part of the language. Sort when order matters. A find returns a value that rules can store, so its list is always sorted.
