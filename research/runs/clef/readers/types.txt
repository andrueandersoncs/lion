**The ideas most worth Lion's attention**
1. **Units as plain JSON values.** The units spec says unit equality is the abelian-group laws, so a unit can be a map from base unit to integer exponent, and equality becomes JSON equality. Its table of unit rules for each operation is a ready spec for stdlib functions. Unit equations are linear over integer exponents, so Lion's solver could solve them.
2. **Units on ids (FSharp.UMX).** A schema on a relation argument could tag what kind of id it holds, so a rule cannot join customer ids against order ids. This fits Lion's logic layer best of everything here.
3. **Pattern checks through schema inclusion.** Clef only warns about redundant type tests, stops the program when no rule matches, and describes no check that a match is complete. Lion could do both checks with schema inclusion. It should also adopt the rule that every `schema/anyOf` alternative binds the same names, and decide whether "no rule matched" is a failure a program can catch.
4. **Active patterns as views.** This would be a schema that applies a function and matches what it returns. Lion would have to say whether that function may run more than once, which Clef leaves to the implementation.
5. **Errors as data.** A Result convention, standard error records with named fields, and diagnostic codes that are never reassigned. Also the trick of an error type that unifies with anything, so one mistake gives one report instead of a cascade.
6. **Grade discipline lessons for Lion's analysis and solver.** Label each derived fact as exact or as a sound over-approximation. Solve theories with disjoint variables in separate queries, since Nelson-Oppen needs stably infinite theories. When the analysis cannot decide, report it rather than silently widen.
7. **Behavior classification for Lion's docs.** Label what Lion leaves open as implementation-defined, unspecified or undefined. At number edges, such as integers past 2^53 if numbers are JavaScript doubles, either fail or document the behavior.

**Limits, trade-offs and contradictions the pages state**
- **The pages contradict each other on rational exponents and "one unification".**
  - The structural-polymorphism page claims one polynomial unification that also covers rational exponents.
  - The grade spec forbids a combined query.
  - The negative/fractional page says there is no single algorithm or complexity bound, and calls rational exponents a separate extension.
  - The error codes list "rational exponent" as a units error.
  - The units spec says principality "does not automatically extend to their combined constraints".
- **Grade discipline trade-off:** falling back to the full support "would type-check and would produce correct code" but would lose sparsity, so the spec makes it an error instead.
- **Structural polymorphism:** it works only at compile time, and inlining can make binaries larger. The pipeline is "as we currently conceive it".
- **Negative/fractional types:** a "proposed extension" that is not normative.
- **The Program Hypergraph:** "a future design goal". The page also says "Recording a relationship does not by itself discharge its proof obligation."
- **Arity:** the page's examples are not all validated compiler paths.
- **Patterns:** a match with no matching rule ends the program and cannot be caught.
- **Units spec gaps:** it has no scale factors between units (abbreviations are exact equalities), and exponents are integers only.
- **The patterns spec states results its own code does not give.** It says "In this example, result is given the value true , because the pattern input matches the second" for a function that returns `Some year`. It also says "This example binds the identifiers x , y , and t1 to the values 1 , 2 , and (1,2) , respectively." when the code binds `t2`. Both are results that were typed rather than run.
