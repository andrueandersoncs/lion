This guide shows how to ask about every value of a type, not only the values your facts hold. A variable that a schema such as value/integer? types, and that no relation goal binds, is solved for: the filters about it become constraints, and Lion works out exactly which numbers meet them.

Solve for the values that meet some filters

Type the variable with schema/fits?, then filter it as you would a bound one. When the filters leave finitely many whole numbers, each is an answer:

{"between": ["find", "?x", ["and", ["schema/fits?", "?x", "value/integer?"], ["number/greaterThan", "?x", 2], ["number/lessThan", "?x", 6]]], "solved for": ["find", "?x", ["and", ["schema/fits?", "?x", "value/integer?"], ["=", 7, ["number/add", ["number/multiply", 2, "?x"], 1]]]], "pairs": ["find", ["array/make", "?x", "?y"], ["and", ["schema/fits?", "?x", "value/integer?"], ["schema/fits?", "?y", "value/integer?"], ["number/greaterThanOrEqualTo", "?x", 0], ["number/greaterThanOrEqualTo", "?y", 0], ["=", ["number/add", "?x", "?y"], 3]]]}

The filters can add, subtract, multiply and divide by known numbers, compare, and use number/min, number/max, number/absolute, and cond. value/number? types a variable that may be any number.

Ask whether a value exists, or prove that none does

When there are infinitely many values, they cannot each be an answer, but exists can still ask whether there is one, and not whether there is none. Lion decides it for every number, not only the ones it tried:

{"an odd number above 10": ["query", ["exists", ["?n", "?k"], ["and", ["schema/fits?", "?n", "value/integer?"], ["number/greaterThan", "?n", 10], ["=", ["number/subtract", "?n", ["number/multiply", 2, "?k"]], 1], ["schema/fits?", "?k", "value/integer?"]]]], "no whole number doubles to 7": ["query", ["not", ["exists", ["?n"], ["and", ["schema/fits?", "?n", "value/integer?"], ["=", ["number/multiply", 2, "?n"], 7]]]]]}

Each query gives [{}] when its goal holds and [] when it does not.

Check what a function does for every input

A lambda you defined runs on the values the solver stands for, by its body, so a rule about what it returns is checked for every input at once. A schema of a record with typed fields stands for every such record. Here a careful withdrawal never leaves an open account below zero, for any balance and any amount, while a careless one can:

["begin", ["define", "careful", ["lambda", ["account", "amount"], ["cond", [["number/lessThan", ["object/get", "account", "balance"], "amount"], "account"], ["else", {"balance": ["number/subtract", ["object/get", "account", "balance"], "amount"]}]]]], ["define", "careless", ["lambda", ["account", "amount"], {"balance": ["number/subtract", ["object/get", "account", "balance"], "amount"]}]], ["define", "overdraws", ["lambda", ["withdraw"], ["query", ["exists", ["?account", "?amount"], ["and", ["schema/fits?", "?account", {"balance": "value/integer?"}], ["schema/fits?", "?amount", "value/integer?"], ["number/greaterThanOrEqualTo", ["object/get", "?account", "balance"], 0], ["number/greaterThan", "?amount", 0], ["number/lessThan", ["object/get", ["withdraw", "?account", "?amount"], "balance"], 0]]]]]], {"careful": ["overdraws", "careful"], "careless": ["overdraws", "careless"]}]

Know what it cannot decide

Lion decides sums of numbers times known numbers, comparisons of them, and equality of values, so every question it decides has one answer. Anything else, such as a product of two unknowns or a string function, waits for values: the solver lists the values of the variables it needs, from what it can decide, and runs it on each, as plain code would:

{"factors of 6": ["find", ["array/make", "?x", "?y"], ["and", ["schema/fits?", "?x", "value/integer?"], ["schema/fits?", "?y", "value/integer?"], ["number/greaterThanOrEqualTo", "?x", 1], ["number/lessThanOrEqualTo", "?x", 6], ["number/greaterThanOrEqualTo", "?y", 1], ["number/lessThanOrEqualTo", "?y", 6], ["=", ["number/multiply", "?x", "?y"], 6]]], "names": ["find", "?name", ["and", ["schema/fits?", "?x", "value/integer?"], ["number/greaterThan", "?x", 7], ["number/lessThan", "?x", 11], ["=", "?name", ["string/concat", "room ", ["number/toString", "?x"]]]]]}

When the values a waiting goal needs are infinitely many, they cannot each be tried, and the question fails, naming what the solver cannot reason about. A variable whose filters allow infinitely many values cannot be an answer either:

["query", ["exists", ["?x", "?y"], ["and", ["schema/fits?", "?x", "value/integer?"], ["schema/fits?", "?y", "value/integer?"], ["=", ["number/multiply", "?x", "?y"], 6]]]] ["find", "?x", ["and", ["schema/fits?", "?x", "value/integer?"], ["number/greaterThan", "?x", 2]]]
