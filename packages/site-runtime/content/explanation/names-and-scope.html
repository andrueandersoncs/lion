Every string in a Lion program might be a name. This page explains which strings are names, where they come from, how a lookup finds them, and how long they last.

Environments are chains

An environment is a record of bindings with an optional parent. Looking up a name checks the current environment, then its parent, and so on to the top. A run starts with one top-level environment holding whatever the host gave it, usually the standard library.

Calling a lambda makes a new environment for its parameters whose parent is the environment where the lambda was created, not where it is called. That is lexical scope: a lambda remembers the names around it.

["begin", ["define", "counterFrom", ["lambda", ["start"], ["lambda", ["step"], ["number/add", "start", "step"]]]], ["define", "fromTen", ["counterFrom", 10]], ["define", "start", 1000], ["fromTen", 5]]

The global start is 1000, but the inner lambda sees the start it was created with, 10.

A string is a name where a scope declares it

JSON has one kind of string, so Lion decides which strings are names by where they are written, before the program runs. A string that a scope around it declares is a name; any other is data. A scope declares its bindings from its start: the names the host gave the run and the database's relations, the names the program defines anywhere at its top level and the relations and schemas it declares, and, for a lambda, its parameters and the names its body defines. What a string means therefore never depends on the order things run in: a binding made later, by eval for instance, never turns data that code already holds into a name. That holds in the parts of a find, a rule, or any other logic form as in plain code: they are read by the scopes they are written in, whenever the form runs. The first element of an array is the one place a string is always a name, since it names what the array does: one no scope declares is looked up where the call runs, so a relation that eval declared can be asked about after it.

["begin", ["relation", "seen", ["x"]], ["fact", ["seen", 1]], ["eval", ["quote", ["define", "later", 5]]], {"plain": "later", "find": ["find", "?v", ["=", "?v", "later"]], "in eval": ["eval", ["quote", "later"]]}]

Because a body declares what it defines from its start, functions can name each other in any order, which mutual recursion needs:

["begin", ["define", "greet", ["lambda", [], ["string/concat", "hello, ", "name"]]], ["define", "name", "Ada"], ["greet"]]

Calling greet before name is defined fails with UndefinedYetError, rather than greeting the string "name".

Since the scopes settle it before anything runs, a tool can read it too. The graph editor shows under every string what it is there: a name, with what binds it (a parameter, a local or top-level define, a relation, a schema, or the environment), a logic variable, or data. Selecting a name marks its binding and every other string that means it, and a string that only a name could be, such as a misspelled module/name, is marked as an error before the program runs. analyze gives hosts the same reading.

define binds in its body; set! changes a binding

define binds in the body it stands in: inside a lambda, the lambda's call, so a helper value inside a function stays inside it, as in Scheme. To change a name around a lambda, such as the state an app's callbacks update, use set!:

["begin", ["define", "total", 0], ["define", "add", ["lambda", ["n"], ["begin", ["define", "doubled", ["number/multiply", "n", 2]], ["set!", "total", ["number/add", "total", "doubled"]]]]], ["add", 1], ["add", 2], {"total": "total", "doubled": "doubled"}]

doubled is the string outside add, since nothing outside declares it.

Parameters shadow globals, and forms

A parameter with the same name as a global hides the global inside the lambda's body. Because standard library names contain a /, choosing parameter names without one keeps them from shadowing a library function by accident. A parameter or a define may also take a special form's name, such as fact or in: where it is in scope, an array that starts with it is a call, and everywhere else the form.

Strings that name nothing

A string that no scope declares is itself, which is what lets a program write "open" for a status without any quoting. The cost is that a misspelled name would quietly become a string: ["number/ad", 1, 2] would be a call to a string, and "value/intger?" as a schema would be a string that only the same string fits.

So Lion looks at one more thing. A string of the form module/name that reads as a misspelled name is an error. It reads that way when other names of its module are bound, or when a bound name is a letter or two away, which the error then suggests. Any other string with a slash in it, such as "n/a" or "text/plain", is data as before.

["array/map", ["array/make", 1, "two"], "value/numbr?"]

A host that adds functions under its own module gets the same check for them: once "shop/stock" is bound, "shop/stok" is an error. Inside quote, a string is always data.

What lasts between runs

Names last for one run. Each run, whether a call to run, one file on the command line, or one example on this page, starts with a fresh environment, so nothing a program defines leaks into the next.

The logic database is different. It is not part of the environment; it is a separate store that a host can pass to several runs, and that the command line keeps in a file. Relations and schemas declared in a shared database are bound by name in every run that uses it, unless the host binds the same name. This split is deliberate: definitions are code, and code is re-run, while facts are state, and state persists.

Functions are Effects

A Lion function returns an Effect, a description of work, rather than a plain value. Evaluation is itself an Effect, so a function can do anything an Effect can, such as wait for a network call or fail with a typed error, and the evaluator composes it with everything else. Host functions may return plain values or Effects; Lion handles both. This is why func/callback exists: it turns a Lion function into an ordinary JavaScript function for APIs that expect one.
