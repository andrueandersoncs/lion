The logic layer stores facts in relations, derives more with rules, and answers queries. Relations, goals, and logic variables are ordinary Lion values, and answers are plain Lion data. For the rules every program must follow, see Logic database guarantees.

Logic variables

  • An unbound string of the form "?name" evaluates to a logic variable. See Strings for the exact form.
  • The same name refers to the same variable throughout one goal or rule.
  • "?_", and any name starting with ?_, is anonymous: each occurrence is a separate variable, it never appears in answers, and inside not it matches anything.
  • Logic variables must be direct arguments of a goal or call, not nested inside lists or records.

Goals

A goal is a value that a query, rule, or invariant can solve. Goals are built by calling a relation, by not, and, or, =, and in, by calling a graph algorithm, and by calling a pure function on logic variables, which makes a filter. The booleans true and false are goals that always and never hold.

relation

["relation", name, [column, ...]] ["relation", name, [column, ...], {"key": column-or-columns}]
  • Declares a relation in the current database and binds name to it in the global environment. Returns the relation, a function: calling it with one term per column builds a goal.
  • Column names must be distinct. Options are read as written, not evaluated; the only option is "key".
  • With a key, the relation holds at most one row per key: adding a fact whose key is present replaces the old row. A key can name one column or several.
  • Declaring a relation that already exists with the same columns and key does nothing; declaring it with different ones fails.
["begin", ["relation", "order", ["id", "status"], {"key": "id"}], ["fact", ["order", 1, "open"], ["order", 1, "paid"]], ["query", ["order", "?id", "?status"]]]

fact

["fact", goal, ...]
  • Adds each fact, a relation call with JSON data and no logic variables, and returns the facts given.
  • A relation's facts are a set; adding a fact that is present changes nothing.
  • For a keyed relation, a fact replaces the row with the same key; within one form, the last fact for a key wins.
  • A relation that rules aggregate into, or that a graph algorithm computes, cannot have facts.
  • The form is one change: it is checked in full, made in full, and checked against every invariant, or it fails and changes nothing.

retract

["retract", goal, ...]
  • Removes each fact, and returns the facts that were present and removed.
  • A row of a keyed relation is removed only when every column matches.
  • Facts derived by rules cannot be retracted; derived answers update on the next query.
  • Like fact, the form is one all-or-nothing change.
["begin", ["relation", "edge", ["from", "to"]], ["fact", ["edge", "a", "b"], ["edge", "b", "c"]], ["retract", ["edge", "a", "b"], ["edge", "x", "y"]]]

rule

["rule", head, goal, ...]
  • Adds a rule: head, a relation call, holds for every way of satisfying all the goals. Returns the rule as written, with values as evaluated.
  • Head arguments can be values, variables bound by the body, computed values from pure functions, and aggregates.
  • The rule is checked when added: every head variable must be bound by the body, every goal must be safe, and the whole program must stay stratified and terminating. A rule that fails a check is not added.
  • An or in the body makes one rule with several alternatives.
  • Adding a rule the database already holds, one a snapshot would write the same way, changes nothing.
  • Adding a rule is one all-or-nothing change, checked against every invariant.

query

["query", goal] ["query", goal, options]
  • Returns one record per distinct answer, with one key per named variable, without its ?. A goal with no variables returns [{}] when it holds and [] when it does not.
  • Without the "order" option, answers come in the order they are found, which can change between versions of Lion.
  • Options sort, page, and assert on the answers; see Query options.
["begin", ["relation", "edge", ["from", "to"]], ["fact", ["edge", "a", "b"], ["edge", "a", "c"]], {"targets": ["query", ["edge", "a", "?to"], {"order": "to"}], "holds": ["query", ["edge", "a", "b"]], "fails": ["query", ["edge", "b", "a"]]}]

why

["why", fact]
  • Returns a tree that explains how fact, a relation call with no variables, holds, or null when it does not.
  • Each node has a fact, and either "given": true, "computed": true for a graph algorithm's row, or the rule that derived it with the premises it used under because.
  • Premises are facts, {"check": call} for filters, and {"absent": pattern} for negations.
  • An aggregated fact lists every match it combines under matches; for min, max, and shortest, it explains the match that produced the value.
  • Explanations use every relation computed in full.

not

["not", goal]

With a relation call, holds when the call has no matches. Every named variable in it must be bound by an earlier goal. With a boolean, returns its negation.

and

["and", goal, ...]

Holds when every goal holds, sharing variables between them. With only booleans, returns their conjunction.

or

["or", goal, ...]

Holds when any goal holds. With only booleans, returns their disjunction. Goals combining and and or may expand to at most 64 alternatives.

{"and": ["and", true, false], "or": ["or", false, true], "not": ["not", true]}

=

["=", term, term]

Binds an unbound variable on either side to the other side's value, or tests that both sides are equal. Without logic variables, it is structural equality of JSON values, and identity for other values.

["=", ["quote", {"a": [1, 2]}], {"a": ["array/make", 1, 2]}]

in

["in", element, list]

With an unbound element, binds it to each distinct item of the list; with a bound one, tests membership. The list must be bound first. Without logic variables, it is plain membership and returns a boolean.

["in", "b", ["array/make", "a", "b"]]

snapshot

["snapshot"]
  • Returns a begin program that rebuilds the current database: a relation form per relation, a fact form per relation with facts, every rule, and every invariant, in that order.
  • Strings that would evaluate to something else are written inside quote: logic variable names, relation names, names bound in the environment, and namespaced names such as "number/add". Lists and records are quoted too.
  • Fails if a rule or invariant holds a value that is not JSON data, such as a function.
["begin", ["relation", "note", ["text"]], ["fact", ["note", "plain"], ["note", ["quote", "?x"]], ["note", ["array/make", 1, 2]]], ["snapshot"]]

invariant

["invariant", goal, {"assert": "none"}] ["invariant", goal, {"assert": "some"}]
  • Adds a query assertion the database keeps: the goal must have no answers ("none") or at least one ("some"). Returns the invariant as written.
  • The goal is compiled and checked like a query's. The options record is read as written and must hold exactly "assert".
  • The invariant must hold when added; otherwise it is not added.
  • After that, every fact, retract, and rule form is checked against every invariant once it has made all of its changes. A form that breaks one, or whose check fails, is undone and fails, leaving the database exactly as it was.
  • Adding an invariant the database already holds changes nothing. Invariants cannot be removed.
["begin", ["relation", "edge", ["from", "to"]], ["invariant", ["edge", "?x", "?x"], {"assert": "none"}], ["fact", ["edge", "a", "b"], ["edge", "c", "c"]]]
