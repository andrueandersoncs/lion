# How the logic engine follows a change

This is how `packages/core/src/logic/weights.ts` keeps derived rows up to date. It is written for people changing the engine. What a Lion program can observe is in the README's [Guarantees](../../../../README.md#guarantees); nothing here changes an answer, only what an answer costs.

A change to facts is followed through what was derived, so it costs what it reaches and not what the database holds. Every derived row has a weight: the number of its candidates, each a fact or an answer of a rule's body that gives the row, and the row holds while its weight is above zero. A change takes away the candidates that used a row a relation lost and adds the ones that use a row a relation gained, wherever the goal that matched the row stands in the rule: in its body, under `not`, in a `find`, in a goal used as a value, or in its head. An aggregate keeps the values of its candidates counted, so a count, and a sum or a mean of whole numbers, change by one candidate, and every other aggregate combines the values that are left. Rows that give each other cannot hold each other up. A candidate has a level, one above the highest level of the rows of its own group that its answer used, and a row is held from the least level of its candidates. A change is settled level by level, lowest first, so a row whose first candidate is gone holds only where a candidate that rests on lower levels still gives it. Deriving from nothing is the same work, for a change that adds every fact.

A rule that [invents](#existential-rules), a [key](#keys), and an equality rule are followed the same way, whatever the rule's goals look like. The answers of a rule that invents are counted as rows are, and each is asked, at the end of the stage it is first held in, whether a row held by then gives its head. Two values that a key or an equality rule makes one are a pair with candidates of its own. A row that comes beside a row with its key is read from the level after, when the pair has made the two one, so no rule finds two rows with one key, not even a rule of the group that derives them. A row that holds a value its class no longer writes ends at the level the pair is held from, and is kept beside the row it became, so taking away the fact that made two unknowns one gives back the rows that held them apart. `why` finds the answer that gives a row when it is asked, from the level the row is held from, so a change keeps no explanations and works none out. Where a key or an equality rule made values one, `why` derives the group's answers again once after a change, to tell its rows through the values made one. Two kinds of relation cannot be followed row by row: one whose rule holds a [function from the host](#host-functions-in-rules) that does not say it reads only its arguments, or asks [`assuming`](#asking-what-would-hold), which asks the database as it is and never as it was before the change, and one whose rule reads a changed relation through a schema instead of a relation goal. Such a relation is derived again and compared with what it was, so the relations that read it are still followed. That happens when something has read it since the last change. Otherwise nobody is waiting for it, and it is forgotten, with the relations that read it, until something reads it.

A `rule` form is followed the same way: the relations whose rules changed are derived again and compared, and every other relation keeps its rows. A change an invariant refuses is followed back, so what was derived before it is still there. That holds also when following the change found two rows with one key that the key cannot make one. Such a group keeps its rows, exactly as deriving from nothing would give them, with why they break the key (`Support.problem`), and a question that reads the group fails with it at once, so an invariant that reads it refuses the change without deriving anything. The change is followed past the group: a group that reads it is set aside as it was (`Model.behind`), since nobody can read it, and every other group is brought up to date. A refused change is followed back through the same model, past the groups set aside; a kept one forgets them, and what goal-directed queries derived, which was set aside too. The next change is followed through the rows that break the key, and checks the rows it gives and the rows that stood beside another with their key (`Support.clashing`), so it never reads every row. The message is told from the rows there are, not from what a run saw: of the pairs of rows with one key, the one whose rows sort first; the rule it names is the least that gives the derived row now, found by asking each rule's body with the row's values, as `why` does, and through the rows that became it when a key or an equality rule made a value one with another (`Chase.formers`). So a group derived from nothing and one that followed changes say the same, by construction. Which unknowns facts hold says whether a key can make two rows one, so when a fact that holds an unknown comes or goes, the rows that hold the unknown are paired again with the rows that have their key, and two rows that part take away what they gave when they met. A [goal-directed query](#goal-directed-queries) keeps what it derived and follows changes too, for up to 32 different queries; past that they are answered again when asked.

A goal of a body reads its rows through a later relation goal that has fewer rows for the answer (`fewest` in `model.ts`) only where both read a set of rows that hold now. The rows a group reads of itself while rows of it have ended (`Both`), and a relation as it was before a change (`Was`), are read only by their own goal: which of their rows an answer may use depends on levels, and a database derived from nothing reads them the same way a followed one does, so comparing the two could not tell a cover that read them wrongly.

## Where to read further

- `weights.ts`: candidates by level (`Entry`), settling a change level by level (`settle`, `settleLevel`), stages for rules that invent (`step`), pairs a key or an equality rule makes one (`pairUp`, `repair`, `relink`), and aggregates as counted folds (`Fold`, `Tally`).
- `model.ts`: a body's goals matched one at a time, each through an index on the values it knows (`candidates`), or through a later relation goal with fewer rows for the answer (`fewest`, `latersOf`).
- `maintain.ts`: the order groups are followed in, the groups set aside because they read rows that break a key (`setAside`, `broken`), and the two kinds of relation that are derived again and compared.
- `database.ts`: the goal-directed queries a change keeps aside while invariants check it (`Aside`), following a refused change back (`followBack`), and forgetting the groups set aside once a change is kept.
- `logic/tests/weights.test.ts`: the property that compares every row and every entry's levels and counts between a database that followed changes and one derived fresh. Run it with `LION_RUNS=5000` before changing the engine.
